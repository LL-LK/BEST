## 0. 术语对照（给非算法背景读者）

| 说法 | 大白话 |
|------|--------|
| 可复现性 | 同一件事，同样条件下做两次，得到同样的结果。像同一道菜按同一菜谱做两遍，味道应该一样 |
| 固定清单（frozen manifest） | 开跑前把「用的是哪份数据、哪版代码、哪个模型、哪段提示语、什么温度」全部抄下来存档，少一样就不算数 |
| 指纹（fingerprint） | 给一堆内容算一个唯一的「身份证号」（sha256）。内容变一位数字，身份证号就完全不同 |
| 端到端 trace（轨迹） | 一次任务从头到尾的「黑匣子记录」：模型说了什么、调了哪个工具、传了什么参数、报错没有、重试几次、最后怎么答的 |
| 一致率 | 多次运行之间「答案相同的比例」。100% 才是完全可复现 |
| 众数一致率 | 跑 5 次，取出现次数最多的那个答案当「标准」，看其余几次有多少跟它一样。比「两两互相比」更抗个别抽风 |
| 结论卡 | 把一段自然语言回答压缩成「几个关键数字 + 几个关键实体（表名/列名/URI）+ 属于哪类回答」的小卡片，便于机器比对 |
| 反证夹具 | 故意做坏的样本。检测器要是连明显的坏都抓不出来，说明它自己在罢工 |
| 效率比 η | 「理论上最少要发几次请求」÷「实际发了几次」。越接近 1 越不浪费 |
| 首次可用率 | 用户问一句，不用再追问、不用自己修参数，就直接拿到能用的答案 |

## 1. 目标与非目标

### 1.1 目标

1. **把「不可复现」拆成四笔账**：模型采样不稳、代码/配置不稳、网络与服务端不稳、时间与环境变化。
   E6 要用四路对照把它们分开，最终报告能说出「这次不一致，**是模型的锅 / 代码的锅 / 数据库的锅**」。
2. **量化四个一致率**：工具选择一致率、参数一致率、返回数据一致率、最终结论一致率（§5）。
3. **产出可归档的端到端 trace**：模型调用 / 工具调用 / 错误 / 重试 / 最终输出全记录，
   支持事后单步重放与归因（§4）。
4. **量化效率**：请求数、墙钟、冗余调用、重试、分页行为，并给出与理论最小值的比值（§6）。
5. **量化用户可用性**：首次可用率、错误可操作性、澄清质量、答案自解释性、诚实降级（§7）。

### 1.2 非目标（明确划走，避免实验被稀释）

- ❌ **不评判对错**：工具选错、参数传错、数据取错、解释说错——分别是 E1/E2/E3 的活。
  E6 只在「两次不一样」时记录差异，判定责任归属后**把结论移交对应实验**。
- ❌ **不测漂移大小**：那是 E7。E6 只做「有没有漂」的门禁判定（指纹前后比对），不做定量。
- ❌ **不做性能优化**：E6 只报数，不调参、不改实现。
- ❌ **不做用户访谈/大规模问卷**：本仓无真实用户池，可用性以**客观可机读指标为主**，
  主观分仅作补充且必须声明效力不足（§7.3）。
- ❌ **不并入 `evals/scoring-rubric.yaml` 五维加权**（权重和已被代码锁死 1.0，沿用 E1/E2/E3 约定），
  E6 单独出 `REPORT.md`。

## 2. 被测对象与四路对照（E6 的核心结构）

**被测对象（SUT）**＝「大语言模型 + astro-best 工具面（`references/tools.schema.json` 的 7 个原子工具）」
的整体端到端链路。

**关键现实约束（必须诚实面对）**：本仓**主链路不调用大模型**（`rag/astro_rag.py` 是纯标准库检索器，
无模型、不联网）。因此「模型版本 / 温度 / 随机种子」是**外部 harness 代入**的变量，E6 的角色是
**记录并在可能范围内钉死它**，而不是声称能控制它。文档中所有涉模型项都标注 `external`（外部观测）。

### 2.1 四路对照矩阵

| 路 | 名称 | 怎么跑 | 冻住了什么 | 剩下谁在变 | 回答什么问题 |
|----|------|--------|-----------|-----------|-------------|
| **R0** | 工具层固化回放 | 无模型，按预先写死的调用序列直接打工具；走 E2 的 `SnapshotTransport` | 模型、网络、服务端、时间 | 只有代码与环境 | **地板线**：连 R0 都不一致 → 是代码/环境 bug，不是模型问题 |
| **R1** | 同日在线重跑 | 真实 agent 跑 5 次，同一天连续完成 | 任务集、schema、模型配置 | 模型采样 + 网络抖动 | 端到端日常可复现性（**主场景**） |
| **R2** | 跨日在线重跑（D+7） | 7 天后同条件再跑 5 次 | 同上 | 上面全部 + **数据漂移** | R2 与 R1 的差 = 漂移信号 → **移交 E7** |
| **R3** | 快照回放重跑 | 真实 agent 跑 5 次，但网络层被 `SnapshotTransport` 顶掉，`rate_limit=0.0` | 网络、服务端、时间 | **只有模型采样**（+代码） | 剥离环境噪声后的**纯模型侧**可复现性 |

**归因规则（四路差值即答案）**：

- `R3 不一致率` ≈ 模型侧不稳定（代码与数据都冻住了，只能是模型）；
- `R1 − R3` ≈ 网络/服务端抖动引入的不稳定；
- `R2 − R1` ≈ 数据漂移（移交 E7 定量）；
- `R0 不一致率 > 0` → **立即阻断**，这是代码层的确定性 bug，与模型无关。

> R3 复用 E2 已设计的 `SnapshotTransport`（顶掉 `client.session.get/post`）与 `BestClient(rate_limit=0.0)`；
> E2 若先落地，E6 直接 import 其 transport，不重造。R3 的快照必须**连失败/软 404 的回包一起冻**
> （E2 §3.1 已强调：只冻结果 CSV 就测不到分页/软错误）。

## 3. 固定清单（frozen manifest）—— 八项，一项都不能少

开跑前生成 `run_manifest.json`，八项全部落盘；**任一项缺失 → 本 run 无效（阻断项）**。
每项都给出本仓的取值方法（可命令化，不凭印象）。

| # | 固定项 | 本仓怎么取（命令/口径） | 备注 |
|---|--------|----------------------|------|
| 1 | **BEST 数据版本** | 站点无显式版本号 → 用 **canary 指纹**：固定 5 条探针查询（ps1 / gaia_dr3_18 / scr_galah / stripe82 / xpsp 各一条定参锥搜 + 一次 `count`），对规范化结果算 `bestfp:sha256:<64hex>`。run 前后各算一次：一致 → `STABLE`；不一致 → 本 run 标记 `DRIFTED`（不判失败，但必须声明） | 与 E2 §M6 的"版本一致率"同源，E6 只做门禁不做定量 |
| 2 | **Skill 版本** | ⚠️ 本仓 **禁版本号** 且 **无 `.git`**（实测：仓库根无 `.git` 目录）→ 用**内容指纹**：`skill_fp = sha256(排序后的 "相对路径|大小|内容sha256" 拼接)`，扫描 `src/ ops/ evals/ contracts/ references/ static/ agents/ SKILL.md README.md architecture.md manifest.yaml`，**排除** `temp/ __pycache__/ *.pyc .workbuddy-ai/` | 复用 `ops/verify_tree_integrity.py` 的排除口径，不另立一套 |
| 3 | **模型版本** `external` | `model_id`（必须钉具体版本串，**禁用 `latest` / `-latest` 别名**）+ provider + endpoint + 权重快照日期；厂商不暴露时记 `"opaque"` 并在报告披露 | 用别名 = 阻断项 |
| 4 | **system prompt** | prompt 全文落盘 + `prompt_fp = sha256(文本)` + 字节数 + 模板 id | 改一个标点指纹就变 |
| 5 | **工具 schema** | 两个都要：① `references/tools.schema.json` 的 sha256；② 暴露侧工具清单**规范化后**（键排序、去描述字段）的 sha256（清单本体见 `references/llms.txt`） | 只记一个会漏掉"代码与暴露面漂移" |
| 6 | **评测数据** | 任务集文件 sha256（E6 任务集见 §3.1）+ 快照 id（`snapshot_id`）+ 快照清单指纹 | 任务集改一个字，历史分数不可比 |
| 7 | **温度与随机种子** | `temperature`（建议 **0.0**）、`top_p`、`seed`（记 `requested` 与 `honored` 两态：厂商不保证时 `honored=false`）、`max_tokens`、`reasoning_effort`（若开推理模式） | `honored=false` 必须在报告披露，不得当作已固定 |
| 8 | **执行日期** | `run_date`（ISO 日期）+ `run_started_utc` + 时区 + `crossed_utc_midnight: bool` | 跨 UTC 日界会让服务端日期相关行为变化，必须记录 |

`rate_limit`（默认 2.0 s/请求，直接污染墙钟）、HTTP 缓存开关、并发度、Python 版本、requests 版本、

## 4. 端到端 trace：规格、脱敏与归因（E6 的一等产物）

### 4.1 trace 事件 schema

一条 trace = 一个 JSONL 文件（一行一个事件，便于流式追加与大文件 diff）。事件字段：

```yaml
# 每个事件共有的头（必填）
seq:            # 序号，从 0 单调递增（断号 = trace 不完整 = 阻断）
ts_utc:         # ISO8601 UTC 时间戳
ts_mono:        # monotonic 秒数（算间隔用，不受系统改时间影响）
run_id:         # 一次运行的唯一 id
task_id:        # REPRO-nn
attempt:        # 第几次尝试（重试递增）
parent_seq:     # 触发本事件的事件序号（用于串成因果链）；根事件为 null
layer:          # model | tool | network | harness
type:           # 见下表
payload: { }    # 事件专属内容
payload_fp:     # sha256(规范化 payload)，用于跨 run 比对
```

| type | 谁产生 | payload 关键字段 |
|------|--------|-----------------|
| `run_start` | harness | 完整 `run_manifest` 指纹（§3 八项） |
| `model_request` | harness | `model_id`, `temperature`, `seed`, `prompt_fp`, `messages_fp`, `schema_fp` |
| `model_response` | harness | `raw_fp`, `latency_s`, `tokens_in`, `tokens_out`, `finish_reason`, `tool_calls[]`（抽出的调用意图） |
| `tool_call` | agent→工具 | `tool`（名）, `args`（原始）, `args_norm`（归一化后，见 §5.2）, `args_fp` |
| `tool_result` | 工具→agent | `envelope_fp`, `status.ok`, `status.error_code`, `cost.*`, `provenance.data_hash`, `provenance.stable_uri`, `content_trust` |
| `error` | 任一层 | `layer`, `error_code`, `message_fp`, `is_retryable` |
| `retry` | harness/agent | `retry_of_seq`, `reason`, `backoff_s`, `strategy_changed`（是否换了参数/工具） |
| `clarification` | agent→用户 | `missing_dims[]`, `options[]`, `turn_index` |
| `final_answer` | agent | `answer_fp`, `conclusion_card`（§5.4）, `cited_uris[]`, `caveats[]` |
| `run_end` | harness | `total_requests`, `total_elapsed_s`, `outcome`（success/clarify/reject/fail） |

### 4.2 脱敏红线（写入 trace 前强制执行）

- **禁止**落盘任何凭据：`BEST_API_TOKEN`、`Authorization` 头、`Cookie`、OAuth `access_token`
  （沿用 `agents/openai.yaml` 的 honesty_stance「凭据只读环境变量，代码零凭据字面量」）；
- URL 中的 token 查询参数必须替换为 `***`；
- 站点行数据可全文落盘（本就是 `content_trust=untrusted` 的数据面），但需带 untrusted 标记。

### 4.3 分层归因决策表（回答"到底是路由错误、参数错误还是数据库返回错误"）

按表**从上到下第一条命中即用**，不重叠：

| 序 | 判定条件 | 归因 | 含义 |
|----|---------|------|------|
| 1 | `tool_call.tool` 不在 schema 的 7 个工具名内，或是 CLI/Python 类/伪造工具名 | **ERR_ROUTE**（路由错误） | 找错了门 → 移交 E1 |
| 2 | 工具名对，但参数名不存在 / 类型错 / 值越界（半径 >18000″、坐标越界） | **ERR_PARAM_SCHEMA**（参数错误·硬错） | 传错了话 → 移交 E1；**这一条与稳定性无关，任何一次运行都会错** |
| 3 | 工具名与参数都合法，但**与同任务其他 run 的众数不一致**（单位未换算、表选错、半径差一档） | **ERR_PARAM_UNSTABLE**（参数不稳定） | **这才是 E6 要抓的模型侧不稳定** |
| 4 | 工具名与参数都与众数一致，但 `status.ok=false` 且 `error_code ∈ {E_SOFT_404, E_NO_SQLID, E_BACKEND, E_NAME_UNRESOLVED}` | **ERR_BACKEND**（数据库/服务端返回错误） | 不是我方的锅；若仅在 R2 出现 → 转 E7 |
| 5 | 工具名与参数都与众数一致、`status.ok=true`，但 `data_hash` 与基线不符 | **ERR_BACKEND_DRIFT**（数据内容变化） | 移交 E7 定量；在线路不判 E6 失分 |
| 6 | 以上都不命中，但 `retry` 链上存在 `strategy_changed=false` 的原样重试 | **ERR_RETRY_INEFFECTIVE**（无效重试） | 效率问题，计入 §6 EF4 |
| 7 | 全部一致但 `final_answer` 结论卡与基线不同 | **ERR_CONCLUSION_UNSTABLE**（结论不稳定） | 工具层一致、结论漂移 → 模型解释层不稳 |

> 第 4/5 条**必须**建立在「工具与参数都与众数一致」的前提上，否则会被误判成后端问题——
> 这是本表最容易犯错的地方，实现时顺序不可调整。

## 5. 四个一致率：定义与算法

给定任务集大小 `T`，每任务重复 `N` 次（默认 `N=5`）。四个指标**全部以「众数」为参照**，
并**同时**报告 pairwise 平均值（防止众数被"五五开"的分布掩盖）。

### 5.1 工具选择一致率 TSC（Tool Selection Consistency）

两次运行的工具调用**序列**（去掉连续重复项，保留顺序）比对。

- **严格档** `TSC_strict`：序列完全相等记 1，否则 0；
- **宽松档** `TSC_set`：工具集合相等记 1（顺序不同不扣分），另报顺序 Jaccard；
- **聚合**：`TSC = Σ_t (众数序列的出现次数 / N) / T`；另报 Krippendorff α（名义尺度）作为稳健汇总。

> 为什么用「序列」而不是「集合」：`resolve_name → cone_search` 与 `cone_search → resolve_name`
> 集合相同但语义完全不同（后者是拿结果去反查名字），只看集会漏判。

### 5.2 参数一致率 PAC（Parameter Consistency）

先归一化再比对。归一化表**外置为 YAML**（L1 配置层，改数值不改代码）：

- 角度统一为**度**（`ra` 容差 `1e-6`）；半径统一为**角秒**（容差 `1e-3`）；
- 字符串去首尾空格、大小写不敏感、列名前缀统一（`scr_galah_rztf` ≠ `rztf` 视为**不一致**，列名必须全限定）；
- 枚举类（`catalog`、`mode`）精确比对；列表类（`columns`）按**集合**比对（顺序敏感会误杀）；
- 布尔与 None 精确比对；浮点按上表容差。

两个口径：

- `PAC_field` = 所有参数字段中一致的比例（**松**，能定位到是哪个字段在抖）；
- `PAC_call` = 整条调用全部参数都一致的比例（**严**，主指标）。

> 可复现的地雷：`stable_uri` 里的 `sqlid` 是**易失的**，绝不能进参数比对；用 `stable_uri`
> 的规范化形式（去 `session_id`）比对，引用句柄语义见 `src/ai_tools.py` A-5。

### 5.3 返回数据一致率 RDC（Returned Data Consistency）

三级，**按场景选主口径**：

| 级 | 口径 | 适用 | 抗什么 |
|----|------|------|--------|
| L1 | `data_hash` 全等 | **R3 快照回放**（主） | 什么都抗，但在线场景过于严苛 |
| L2 | 行集 Jaccard（复用 E2 的 `canonical.py` 规范行集，**集合口径**） | **R1/R2 在线**（主） | 抗**服务端分页行序不稳**（E2 已知坑） |
| L3 | 关键字段值容差一致率（`key_fields` 逐字段，容差同 §5.2） | 补充 | 抗"多返回/少返回无关列" |

主指标：`RDC = L2`（在线）/ `L1`（回放），报告中三级都要给。

### 5.4 最终结论一致率 FCC（Final Conclusion Consistency）

**不比对逐字文本**（同一结论的措辞差异无意义），改为抽取**结论卡**再比对：

```yaml
conclusion_card:
  kind:            # value | rowset | refusal | clarification | none   —— 类别必须精确一致
  key_numbers:     # 数值列表（带字段名），按相对容差 1e-6 比对
  key_entities:    # 表名 / 列名 / stable_uri / 错误码 —— 精确比对
  caveats:         # 限定语集合（如"合成测光非实测""xpsp 口径"），按集合比对
```

四个子项全一致记 1，否则 0。`FCC = Σ_t (众数卡的出现次数 / N) / T`。

> **L2（模型/专家）只做一件事**：当两个结论卡在机器口径下不一致、但语义明显等价时
> （如"该区域没有匹配源"vs"0 条命中"），做等价判定。权重 ≤ 10%，**不得翻转 L0 结论**
> （沿用 E2 §7 纪律）。

### 5.5 统计诚实声明（必写进报告）

- **推断单位先声明，再算区间**：四一致率都是**每任务一个比值**再跨任务平均，
  所以跨任务均值的不确定度要按**任务**分组重抽样（`stats.bootstrap_mean_ci`，
  百分位法，固定种子 `20260928` → 跑批逐位可复现），而不是二项比例区间。
  早先实现把跨任务均值 `×100` 当成"成功次数"再除以固定 `100`，等于凭空造出
  100 个观测：**5/5 与 100/100 会算出同一个 [0.963, 1.000]**，区间宽度与真实
  重复次数、覆盖任务数完全脱钩——那不是小样本诚实，是把样本量写死。
  报告因此必须同时给出 `n_tasks_scored`（区间样本量 = 任务数）与 `n_runs_total`
  （总重复次数），两者不可互相替代。
- **零宽区间要标注**：R0 全 18 条一致时组内离散度为零，重抽样只能抽出同一个值，
  区间必然退化为 [1.0, 1.0]。那是**观测到的任务间零离散度**，不等于"真实可复现性
  被证明为 1.0"；`ci_degenerate` 非空即报告必须写明，否则零宽区间会被读成无限确定。
- 单元数 < 2 时区间返 `(0.0, 1.0)`：只有一个任务时任何重抽样都只能抽到同一个值，
  报零宽区间比不报更危险。
- `N=5` 时二项比例的 **95% Wilson 置信区间极宽**（观测 5/5 一致 → 区间约 [0.57, 1.0]；
  4/5 → 约 [0.45, 0.97]）。因此 **E6 只报点估计 + 区间，不做"达标/不达标"的强断言**；
- 一致性汇总用 **Krippendorff α**（比裸一致率更能抵抗偶然一致）；
- 若要比较两版系统（如改 prompt 前后），用 **McNemar 检验**，并在报告中写明 `N=5` 下
  检验效力仅约 0.6–0.7（与 E3 §11 同一诚实口径）；
- 阈值（§8）用于**门禁**时必须在报告里标注"小样本误判风险"。

## 6. 效率指标

数据源：`cost` 信封天然提供 `http_requests` / `elapsed_s` / `rows_returned`（`src/ai_tools.py`，
在 session 唯一出口处实测计数，非估算），无需额外埋点。

> **编号避撞**：效率指标一律用 **EF** 前缀（EF1..EF7），避免与实验编号 E1..E7 混淆；
> 可用性指标沿用 U1..U7。下文所有 "§6 EFx" 均指本表。

| 编号 | 指标 | 算法 | 初始建议阈值（**待标定**） |
|------|------|------|------------------------|
| EF1 | 请求效率比 η | 理论最小请求数 ÷ 实际 `http_requests` 之和（**客户端层口径**，不含适配器层 urllib3 重试 —— 见 `references/tools.schema.json`；有重试的 lane 上 η 会系统性**虚高**，须在报告注明该限定） | η ≥ 0.70 |
| EF2 | 墙钟 P50/P90 | `elapsed_s` 汇总的中位与 P90；**分两种口径**：含 `rate_limit` 睡眠 / 不含 | 报告制，暂不定阈值 |
| EF3 | 冗余调用率 | 多余的 `cone_search`/`crossmatch_batch` 次数 ÷ 总调用数（口径对齐实验 E1 的 §6.4） | ≤ 10% |
| EF4 | 无效重试率 | 满足 §4.3 第 6 条的重试 ÷ 总重试 | ≤ 5% |
| EF5 | 分页效率 | `fetch_page` 次数 vs `count` 真实命中 ÷ 页大小；提前终止/过量翻页均记 | 过量翻页 = 0 次 |
| EF6 | 零请求完成率 | 元数据类任务（REPRO-32 等）实际请求数 = 0 的比例 | = 100%（硬门槛） |
| EF7 | token 成本 `external` | 由外部 harness 提供 `tokens_in/out`；本仓不调 LLM，仅作外部观测列 | 报告制 |

**标定方法（阈值不是拍脑袋）**：先用 10 条任务 pilot 跑 5 轮，取各指标的 P50/P90，
把「P90」设为 warn 线、「P90 × 1.2」设为 fail 线，写回 `evals/repro/rubric.yaml`。
上表数值是**占位建议，必须标注未标定**。

**效率的两个坑（必须记录否则数字不可解释）**：

1. `rate_limit` 默认 2.0 s/请求，会把墙钟拉长数倍 → 墙钟必须分「含/不含限速」两种口径；
2. 网络抖动与 CDN 缓存会让同一任务墙钟差一个量级 → 效率指标**优先看请求数**（离散、稳定），
   墙钟只作参考。

## 7. 用户可用性

可用性评的是「**终端用户**（可能是非天文背景、甚至非程序员）拿到结果后能不能直接用」。
客观指标为主，主观分为辅。

### 7.1 客观指标（L0 程序判定，硬）

| 编号 | 指标 | 算法 | 建议阈值 |
|------|------|------|---------|
| U1 | **首次可用率** | 无需用户追问/自行修正参数即完成任务的比例 | ≥ 0.80 |
| U2 | **错误可操作性三要素齐全率** | 每次失败输出须含 ①稳定错误码（`contracts/error-codes.contract.yaml` 登记项）②人话原因 ③下一步动作；三缺一即不全 | = 100%（硬门槛） |
| U3 | **澄清质量** | 澄清必须指出缺哪个维度（坐标/星表/半径/波段/时间基准/语义口径）+ 给可选项；只说"能具体点吗"记 0（沿用 E1 §6.5 口径） | ≥ 0.90 |
| U4 | **答案自解释性** | 答案须同时给出：单位与量纲、数据版本指纹（或快照 id）、`stable_uri`、`content_trust` 标注；按子项齐全率计 | ≥ 0.90 |

| U6 | **诚实降级率** | 做不到时显式标注 `not_computable`/`not_configured` 而非编造的比例（对齐 `agents/openai.yaml` honesty_stance） | = 100%（硬门槛） |

### 7.2 主观指标（L2，参考，不得翻转 L0）

- **U7 认知负荷**：5 分制（"我能看懂这个结果并知道下一步做什么"）。
  **评阅方式已随 E3 §8 同步改为 LLM-only**：不设 8 名评阅人、不做双评与仲裁、

## 8. 综合分、门槛与阻断项

### 8.1 三面加权（**独立于 `evals/scoring-rubric.yaml`**，单独出 REPORT.md）

| 面 | 权重 | 组成 |
|----|------|------|
| **R 可复现性** | 0.50 | TSC 0.15 / PAC 0.15 / RDC 0.10 / FCC 0.10 |
| **E 效率** | 0.25 | η(EF1) 0.10 / 冗余+无效重试(EF3+EF4) 0.08 / 分页+零请求(EF5+EF6) 0.07 |
| **U 可用性** | 0.25 | U1 0.07 / U2–U4 0.10 / U5–U6 0.08（U7 不进分） |

`pass_score = 0.90`，`warn_line = 0.85`（与现有 rubric 口径对齐）。
**加权分不得覆盖阻断项**：阻断项任一命中，无论总分多少，E6 判 FAIL。

### 8.1.1 ⚠️ 一半的权重建立在未标定的阈值上（E6 最容易被误读的地方）

> **这是 E6 的一处结构性问题，务必先看清再读任何 E6 分数。**
> §8.1 的三面权重是 **R 0.50 / E 0.25 / U 0.25**。但：
> - §6 的 EF1–EF7 阈值列在表里就写着「**初始建议阈值（待标定）**」「上表数值是
>   **占位建议，必须标注未标定**」；
> - §7.1 的 U1–U7 同样只写「建议阈值」，无标定记录；
> - `evals/repro/rubric.yaml` 的 `calibrated: false` 是**当前真实状态**。
>
> 也就是说 **`pass_score = 0.90` 这条放行线，有 0.50 的权重压在没校准的尺子上**。
> 一批实测 η=0.62（低于占位线 0.70）的跑批，可能只是尺子没校准，而不是模型效率差；
> 反过来一批 η=0.75 的跑批也可能只是恰好碰上了占位值。**这两种情况在当前口径下不可区分。**

**处置规则（标定前必须照此读报告）**：

| 面 | 标定前能否用于放行 | 报告怎么写 |
|----|------------------|-----------|
| **R 可复现性（0.50）** | ✅ **能** —— TSC/PAC/RDC/FCC 是**相对一致率**（同一批内比较），不依赖绝对阈值 | 正常报分，**这是 E6 当前唯一有判据的一面** |
| **E 效率（0.25）** | ❌ **不能** | 必须标 `E_uncalibrated: true`，**不参与 pass 判定** |
| **U 可用性（0.25）** | ❌ **不能**（U2/U6 的「必须 100%」是例外，那是绝对红线，与标定无关） | 同上；U2/U6 仍按阻断项 10 执行 |

**标定的最小路径**（§6 已给方法，此处只给工作量）：

```bash
# 10 条任务 × 5 轮 pilot，取各 EF/U 指标 P50/P90，写回 rubric.yaml 并置 calibrated: true
# 预算量级：约 50 次 run —— 是 E5 全量（1100–1500 run）的 1/25 不到
```

> **结论**：E6 在标定完成前**不是「跑完了」，是「跑了一半」**。R0 路已实跑的
> 18/32 覆盖、四一致率 1.0000（Wilson 95% `[0.963, 1.000]`）是**有效的 R 面证据**；
> 而任何引用 E6「综合分」的表述在标定前**都不成立**，除非该分数只由 R 面构成。
> 这与 E1「六维 1.0 不可外引」、E3「metascore 是判定器自证」是同一类纪律。

### 8.2 阻断项清单（任一命中即 E6 FAIL）

1. 固定清单（§3）八项中任一项缺失或未落盘；
2. 模型用 `latest` 别名或未固定 `temperature`；
3. **R0（工具层固化回放）出现任何不一致** —— 代码/环境层不确定，与模型无关，最严重；
4. BEST 数据版本指纹 run 前后不一致却未标记 `DRIFTED`（掩盖漂移）；
5. 反证夹具未 100% 检出（见 §9）；
6. trace 不完整：任一 run 缺 `final_answer`，或 `seq` 断号，或 `tool_call` 与 `tool_result` 不配对；
7. trace 中出现任何凭据原文（脱敏失败）；
8. 任务集中混入相对时间表述任务；
9. 任务覆盖率 < 100%（32 条 × N 次，缺一不可，缺则声明并判 FAIL）；
10. U2 / U6 未达 100%（错误不可操作、或该降级却编造）。

### 9. 反证夹具：检测器必须自证有效

注入 6 类已知扰动，检测器（TSC/PAC/RDC/FCC 的比对器）**必须全部报不一致**：

| # | 扰动 | 该被谁抓到 |
|---|------|-----------|
| 1 | 半径 300″ → 600″ | PAC |
| 2 | 表 `scr_galah` → `xpsp` | TSC（工具序列不变）→ PAC（参数）+ FCC（实体） |
| 3 | 单位错：5 角分当 5 角秒（300″ → 5″） | PAC |
| 4 | 结果删一行 | RDC（L2 Jaccard） |
| 5 | 把 EMPTY 说成 ERROR / 把 ERROR 说成 EMPTY | FCC（kind）+ U2 |
| 6 | 结论数值小数点改一位 | FCC（key_numbers） |

**检出 6/6 = metascore 1.0**；缺任一 → E6 FAIL（沿用 E2 §8 / E3 §9 的仓内纪律：判定器必须先证明自己有效）。

## 10. 已知坑位（结合本仓实测）

1. **无 `.git`**：仓库根无 git 目录 → 拿不到 commit hash。加上治理铁律「禁版本号」，
   Skill 版本**只能**用内容指纹（§3 #2），别写 `v1.2.3`。
2. **站点无数据版本号**：只能靠 canary 指纹（§3 #1），且 canary 自身也可能受网络抖动影响 →
   canary 结果前后不一致时先重跑一次再判 `DRIFTED`。
3. **`temperature=0` 不等于逐位确定**：MoE 路由、批处理、服务端小版本升级都会引入抖动。
   因此 **R3（快照回放）才是纯模型侧稳定性的唯一可信观测**，R1 必然含环境噪声。
4. **seed 支持不一致**：多数厂商不保证 seed 可复现 → `honored` 字段如实记 false 并披露，
   不得当作已固定。
5. **分页行序不稳**：服务端分页顺序不保证 → RDC 主口径必须走**集合**（L2），L1 `data_hash` 只在
   快照回放（R3）中当主指标（E2 已知坑同源）。
6. **`sqlid` 易失**：不可进参数比对与 URI 比对，一律用去 session 的 `stable_uri`。
7. **`elapsed_s` 抖动 + `rate_limit` 默认 2.0s**：效率优先看请求数；墙钟分两种口径记录。
8. **CDS Sesame 外部依赖**：`resolve_name` 走外部服务，快照回放时必须把它一起冻进快照，
   否则 R3 会"假复现"。
9. **HTTP 缓存 / CDN**：可能让第二次运行快很多且回包不同 → 记录缓存开关，效率指标取首次冷跑。
10. **跨 UTC 日界**：日切会让日期相关行为突变 → `crossed_utc_midnight` 必须记录，跨界的 run 单独标注。
11. **推理/思考模式**：若开 reasoning，输出不确定性显著上升，且 token 数不可比 → 单独记录并在报告中分列。
12. **快照回放会掩盖真实漂移**：R3 漂亮不等于线上可复现 → **R1 与 R3 必须同批跑**，
    只报 R3 视为选择性披露（阻断）。

## 11. 执行流程与产物

```bash
# 1) 生成固定清单（八项指纹全部落盘，之后只读）
python evals/repro/run_e6.py --freeze-manifest            # → runs/<run_id>/run_manifest.json

# 2) 四路依次执行（R0 → R3 → R1 → R2；R2 需 D+7 人工触发）
#    --manifest 绑定同一次冻结的清单: 执行前逐项核对 lane/repeat/工具面指纹,
#    任一不符即阻断 (不绑定的批次只能证明"这一轮是什么样", 不能当复现成功证据)
python evals/repro/run_e6.py --lane R0 --repeat 5 --selftest \
    --manifest temp/repro/runs/manifest-<ts>.json                 # 工具层固化回放，无模型
python evals/repro/run_e6.py --lane R3 --repeat 5 --manifest <同一份清单>   # 快照回放（真实 agent）
python evals/repro/run_e6.py --lane R1 --repeat 5 --manifest <同一份清单>   # 同日在线（真实 agent）
python evals/repro/run_e6.py --lane R2 --repeat 5 --manifest <同一份清单>   # 跨日在线（D+7）

# 3) 比对与归因
python evals/repro/run_e6.py --lane R0 --score                   # → 四一致率 + 归因表 + 分组重抽样区间
python evals/repro/run_e6.py --lane R0 --score --efficiency       # → EF1..EF7
python evals/repro/run_e6.py --lane R0 --score --usability        # → U1..U7

# 4) 自证
python evals/repro/run_e6.py --selftest                   # 反证夹具 12/12 才放行（两组，勿按单组 6 条记）

# 退出码沿用 eval_runner 约定：0 全过 / 1 有 fail
```

> **入口形态修正**：初稿写 `python -m evals.e6.run_e6`，该模块路径不存在
> （目录已由 `evals/e6/` 裁决为 `evals/repro/`，且 runner 用的是
> `python evals/repro/run_e6.py` 脚本直跑形态 —— 它会自挂 `sys.path`，
> 与 `evals/eval_runner.py` 同约定，不支持 `import` 入口）。

**两处 fail-closed 门禁（已实装）**：

```bash
python evals/repro/run_e6.py --lane R1                              # 未接模型 → 退出码 1
python evals/repro/run_e6.py --lane R1 --allow-adapter-required     # 仅探接口 → 退出码 0
python evals/repro/run_e6.py --lane R0 --repeat 2 --require-full-coverage   # 有未覆盖任务 → 退出码 1
```

> **必要性一（最直接的 fail-open）**：`--lane R1/R2/R3` 这条分支原本
> `print(adapter_required)` 后 **`return 0`** —— 要一条根本没跑的 lane 却拿到
> 退出码 0，CI 里「E6 通过」与「E6 压根没跑」长得一模一样。现默认返回**非 0**
> 并加 `executed: false` 记账；确属「仅探接口」语义时用 `--allow-adapter-required`
> 显式放行，让意图留在命令行里而不是藏在默认值里。
>
> **必要性二**：R0 的「四一致率全 1.0」只在**已跑的 18 条**上成立。R0 不覆盖需
> LLM 决策的 14 条（clarify / reject-utterance / safety），所以「全 1.0」与
> 「32 条全验过」是两回事 —— 不额外阻断，后者会被读成前者。开了
> `--require-full-coverage` 即把未覆盖任务记 `tasks_uncovered`，且阻断项随分数同出。

## 12. 报告必须披露的 12 个数

1. `skill_fp`（Skill 内容指纹）
2. `bestfp` before / after，及是否 `DRIFTED`
3. `model_id` + `temperature` + `seed.honored`
4. `prompt_fp` + `tools_schema_fp`（代码侧）+ 暴露侧工具清单指纹
5. R0 / R1 / R2 / R3 **四路各自的** TSC、PAC、RDC、FCC（共 16 个数，含 95% 区间
   与其真实样本量 `n_tasks_scored` / `n_runs_total`；区间按任务分组重抽样，见 §5.5）
6. 四路之间的差值：`R1−R3`（环境噪声）、`R2−R1`（漂移，移交 E7）
7. 归因分布：ERR_ROUTE / ERR_PARAM_SCHEMA / ERR_PARAM_UNSTABLE / ERR_BACKEND / ERR_CONCLUSION_UNSTABLE 各多少条
8. 效率：η、请求数 P50/P90、冗余调用率、无效重试率、过量翻页次数、零请求完成率
9. 可用性：U1–U6 各自得分；U7 标 **`review_mode: llm-proxy` 且不进加权**
   （U7 已于 2026-10-03 降为参考项：LLM 代理评分不等于真实用户认知负荷）
10. 反证夹具 metascore（必须 = 1.0）
11. 任务覆盖率与剔除任务清单（含剔除原因）
12. 统计效力声明：`N=5` 下二项比例区间宽度与 McNemar 效力（≈0.6–0.7）；
    跨任务均值的区间按任务分组重抽样并报出任务数，`ci_degenerate` 非空须注明
13. **标定状态声明**（§8.1.1）：`rubric.yaml` 的 `calibrated` 是 true 还是 false；
    为 false 时，`E_uncalibrated: true` + `U_uncalibrated: true` 必须与
    第 8、9 两项**同屏出现**，且综合分必须注明「其中 0.50 权重未标定、不参与 pass 判定」。
    **只报 8/9 两项的数而不报标定状态，等同于把占位阈值当判据 —— 本报告不予采信。**
    「任务间零离散度 ≠ 可复现性被证明为 1.0」

## 14. 建议的推进顺序

1. **先做 trace + manifest 两件套**（无它们后面一切都是空中楼阁）：`trace.py` 写入/脱敏/完整性校验
   + `manifest.py` 八项指纹。用 R0 路（无模型）验证能跑通。
2. **上 R0 + R3 的最小闭环**：10 条任务（含 REPRO-27/28/32）× 3 次，只算 TSC/PAC/RDC + 反证夹具。
   闭环可信再扩，避免"摊子铺太大、判定器没一个可信"（E2 §13 同款纪律）。
3. 补 FCC（结论卡抽取是最难的一块，先手工标注 10 条做 gold 再自动化）。
4. 上 R1（在线），与 R3 同批跑，出 `R1−R3` 差值。
5. 效率与可用性指标最后接（依赖 trace 完整），阈值用 pilot 的 P90 标定。
6. R2 跨日与 E7（漂移）联动，单独排期（D+7）。

### 14.1 R2（D+7）不阻塞主结论 —— 排期裁决

> **本节修正一处排期错误。** R2 需要人工在 **D+7 当天手动触发**（不能自动跑），
> 于是此前 `docs/EVAL-HUMAN-RUNBOOK.md` 的「执行顺序」把「E6 R2（D+7）」排在
> 六个实验的**最后一步**，隐含「E6 要等满 7 天才算完」。这个安排有两个问题：

1. **为 E7 的需求让 E6 阻塞七天。** §2.1 的归因规则写明 `R2 − R1 ≈ 数据漂移`，
   **漂移的定量已移交 E7**（附录 A：E6 只做「有没有漂」的门禁）。
   既然定量不归 E6，E6 就没有理由为它等七天。
2. **R2 缺席不影响 E6 的任何一条归因结论。** 四条归因里，
   `R0`、`R3` 判模型侧、`R1 − R3` 判网络侧**都不需要 R2**；
   唯一涉及 R2 的是漂移，而漂移归属 E7。

**裁决**：

| 阶段 | 内容 | 人工 | 是否阻塞 E6 结论 |
|------|------|------|-----------------|
| 主线 | R0 + R1 + R3 三路 | 0（跑批是脚本） | — |
| 主线收口 | R0/R1/R3 的 TSC/PAC/RDC/FCC + `R1−R3` 差值 | 0 | **E6 到此可出结论** |
| 延后项 | R2（D+7） | 1 次手动触发 | **不阻塞**；R2 缺失时报告须写「漂移未测，移交 E7」 |

> **报告口径**：R2 未跑时，`REPORT.md` 的漂移相关格子必须显式写
> **「未测（D+7 未到）」**，而**不是留空、也不是填 0**。留空会被读成「没漂」，
> 填 0 会被读成「测了，漂移为零」——两者都是 fail-open（铁律 5）。
>
> **人工量**：E6 全部人工 = R2 那 **1 次手动触发**（约 5 分钟）+ 读报告 1 小时。
> 其余全为脚本。R0 路已实跑 5 次、四一致率全 1.0000（Wilson 95% `[0.963, 1.000]`，
> 覆盖 18/32），统计诚实要求：报点估计 + 区间，**不做「完全一致」强断言**。
