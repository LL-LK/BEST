# 质量审计方法论 —— 门禁全绿之后还该做什么

> **这份文档写给下一个人**：接手本仓质量治理、准备开新一轮审计的人。
> 它不讲本仓踩过哪些坑（那是 `docs/architecture/pitfalls.md` 的事），只讲**怎么做审计**：
> 从哪儿入手、用什么手法取证、凭什么下结论、怎么跟别人并行。
>
> **为什么需要它**：2026-10-03 至 10-05 跑过三轮质量审计，产出 100+ 份报告
> （`AUDIT-A*` / `DETECT-*` / `FIX-*` / `VERIFY-*`）。它们全部落在 `temp/`，
> 而 `temp/` 是 gitignored 的临时区 —— **新克隆的人看不到这套方法是怎么形成的，
> 也就看不到为什么门禁要长成现在这样**。本文是那三轮里可复用的部分，
> 原始报告不入库，结论入库。
>
> **配套读**：门禁本体的变更登记与判据口径在 `ops/audit/README.md`；
> 规模预算与注释规范在 `docs/architecture/file-size-budget.md`。

## 1. 循环

一轮完整的质量审计是这七步，**缺一步结论就不成立**：

```
检测（找门禁看不见的）
  → 逐条独立复核        ← 修复者有权推翻检测员（见 §3）
    → 按清单修          ← 每条都带取证，不是"看着不对就改"
      → 本地 git        ← 提交号是证据的一部分，见 §5
        → 规范 reference ← 把结论沉进常驻文档/门禁/回归测试
          → push
            → 重复（换角度，见 §2）
```

**最后两步最容易被跳过，也最值钱。** "规范 reference"指的是把一次性结论变成
**下次不会再犯**的东西：一条判据级红测试、一个收窄级测试、一段写进门禁 docstring 的
判据来源说明。只修不沉淀，下一轮会重新踩同一个坑。

本仓的三轮实例（提交号可 `git show` 复核）：

| 轮 | 提交 | 角度 | 产出 |
|---|---|---|---|
| 1 | `432e631` | 门禁**看不见**什么（注释语义） | 8 路检测 → 14 条 P0 |
| 2 | `ce0a144` | 门禁**判据本身**强不强 | 3×P0 + 33×P1 |
| 3 | `54b07cd` 起 | 门禁**红了是不是真问题**（失败方向）/ 判分口径 / 对外声明面 | 见各 FIX 报告 |

## 2. 立足点：门禁全绿时才值得开检测

**前两轮开始时门禁全绿、测试全绿 —— 那正是值得检测的信号。**

门禁红着的时候检测价值低：它已经在告诉你哪里不对，你再去"独立检测"多半只是
把它的话换个说法重说一遍。全绿意味着**判据当前没有在报任何东西**，这时候才有
必要追问"它是不是本来就看不见"。

配套纪律：**每轮换一个角度，不要把上一轮重跑。**角度清单（本仓三轮的用法）：

1. **门禁看不见什么** —— 门禁只判形态，不判语义。注释说做了 X、代码没做 X，任何门禁都看不见。
2. **门禁判据本身强不强** —— 判据弱 = 门禁永远绿 = 等于没有。
3. **门禁红了是不是真问题** —— 门禁会不会因与被测对象无关的原因变红（狼来了）。

第 3 轮还并了两条：判分口径（分数怎么算出来的）、对外声明面（README/SKILL.md/
manifest 说的话与代码是否一致）。

## 3. 误报率约 40%，修复者必须有权推翻检测员

**检测员会判错，而且这不罕见。**本仓两轮实测：

| 审计 | 检出 | 被修复者推翻 | 推翻率 |
|---|---|---|---|
| D3 横向（`37ec8fe`） | 19 条 P1 | 2 条（P1-19 说 `STD` 成员不存在、`P1-14` 说追不到调用点，事实都错） | ~11% |
| D1 tap（`2c47539`） | 5 条 P1 | 2 条（P1-3、P1-5 判定有误） | **40%** |
| D5 门禁判据（`ce0a144`） | 26 条缺陷 | 1 条被更正（抄件是 4 份不是 3 份） | ~4% |

**所以"修复者必须有权推翻检测员，且必须附依据"是必需的质量控制步骤，不是姿态。**

- 推翻的门槛是**附依据**，不是"我觉得"。`2c47539` 的两条推翻都带实跑：
  P1-5 用变异测试证伪"死代码"说法（禁掉该分支后 3MB 请求体直接拿到 200 OK，
  即上限被完全绕过）。
- **若修复者不许推翻，清单会变成不可质疑的圣经 —— 那是另一种 fail-open。**
  与铁律 5（禁 fail-open）同源：一份没人有权纠错的清单，等于把检测员的
  误判固化成制度。
- 反向也成立：**被推翻的结论要钉成可执行断言**，否则下一个人会重新"修"实现。
  `test/unit/tap/test_p1_comment_contracts.py`（22 条）就是把 D1 三条被误判的结论
  钉死的地方，其模块 docstring 明写"删掉本文件等于允许后人按错误注释'修'实现"。

## 4. 六种找出问题的手法

### 4.1 突变实验 —— 注入缺陷，断言门禁转红

**必须配干净对照组**，否则"永远红"和"永远绿"都能满足 `!= 0`，证据等于零。
这是 `test/unit/meta/test_gate_criterion_red.py` 模块 docstring 的原话
（`test_gate_criterion_red.py:42-43`），也是本仓所有门禁判据级测试的取证纪律。

本仓怎么造假仓（`test_gate_criterion_red.py:67-85`）：门禁都用
`Path(__file__).resolve().parents[2]` 定位仓根，**没有 root 参数可传**，
所以把 `ops/audit/` **整个目录**复制到 `tmp_path` 下的 `假仓/ops/audit/`，
它的 `parents[2]` 就正好变成假仓。必须复制整个目录而不是单文件：门禁之间是
同目录裸名互导，只复制一个会让假仓缺依赖而 `ModuleNotFoundError` ——
那会**伪装成"门禁判红了"**。

判红时别只断退出码：`test_counting_claims_gate.py:97` 用
`assert proc.returncode != 0` **配** `assert str(actual) in proc.stdout` ——
只断退出码的话，门禁因别的原因红也能满足 `!= 0`。

### 4.2 回退验证 —— 证明测试是真锚点

把修复撤掉 → 确认新测试转红 → 恢复 → 确认绿。**没做过这一步的测试，
不知道它是不是承重的。**

实例（`temp/FIX-N1-gates-resume.md` §"新测试是承重的验证"）：

```
$ git stash push -- src/download_progress.py src/download_manager.py
$ python -m pytest ...::TestCrossProcessResumePreservesRecord ... -q
5 failed, 1 passed          # 唯一通过的那条正是"契约不变"守卫, 符合预期
$ git stash pop
$ python -m pytest test/unit/download/ -q   → 197 passed
```

### 4.3 AST 等价性比对 —— 比"测试没红"更强

纯结构重构要证明"行为未变"。"测试全绿"是弱证据：测试可能根本没覆盖被搬走的那段。
更强的做法是两层：

- **词法逐字节**：`git show HEAD:<file>` 的对应行区间与新文件逐行 `==` 比对。
  这一层抓的是 **AST 看不见的东西**：中文右注、`#` 分节横幅。丢掉任何一条
  `comment_audit` 都会红 —— 静默丢失就是造假绿。
- **AST 归一化**：`ast.dump(node, include_attributes=False)` 逐节点比对。
  `include_attributes=False` 丢掉 `lineno`/`col_offset`（换文件必然变），
  保留结构与 docstring 字符串常量本身。
- **反向证明**：剩下的部分也逐个比对，证明"搬走的不只是搬走了，留下的也没被动"。

实例：`temp/FIX-P1-split-test-e3.md` §4 的三层证明（拆 `evals/semantics/tests/test_e3.py`
为两个文件，7 个节点 AST 逐字节相同 + 留下的 10 个类 10/10 未改动）。

### 4.4 判据级红测试 —— 给每个门禁配"它该抓的缺陷"

**防的是"接线绿"**：测试只断言"脚本在盘上且 exit 0"，那把 `main()` 改成
`return 0` 一样满足。突变实验必须在单测里固化，否则下一次改门禁又裸奔。

本仓的动机事件（`test_gate_criterion_red.py` 模块 docstring 记的原案）：
把 `ops/audit/count_code_lines.py` 改成 `return 0` 并提交，再灌一个 1020 净行的文件 ——
门禁 **exit 0**、`code_fingerprint` **不标记**（它只比工作区 vs HEAD，已提交的改动对它不可见）、
全量 1374 个测试**全绿**。**一道门禁可以被一次提交永久废掉，而毫无信号。**

**判据覆盖要均摊。**审计时先盘一遍"哪些门禁只有 exit 0 检查、哪些有判据级测试"，
缺口就是下一轮的活。本仓 `verify_tree_integrity` 曾是八道门里唯一缺的（`ce0a144` 补上）。

### 4.5 三问判据

面对任何一条注释 / 一条测试 / 一处门禁判据，问三个问题：

1. **删掉这条注释/测试，读者会损失什么？** —— 答不上来就是噪声。
2. **我要怎么改坏产品代码，才能让这个测试仍然绿？** —— 答不上来就是锚点。
3. **它红了，是真问题还是环境问题？** —— 这条决定假红（见 §7）。

实例（`temp/DETECT-E1-assertion-strength.md` 批次 3，三处形态一致的
`test_weight_sum_is_one`）：测试只调 `check_weight_sum()`，安全性 100% 押在
"它会抛"上。把容差从 `1e-9` 改成 `0.5`（`evals/nl2tool/graders.py:91`）
→ 测试**仍然绿**，权重被改坏 +0.31 时静默放过。第 2 问有答案 ⇒ P1。
修法是让测试自己断值：`assert abs(sum(M_WEIGHTS.values()) - 1.0) <= 1e-9`，
与已有的对照组形成正交双保险。

**这条判据也用来省事**：`is-None` / `len>0` 这类"弱形态"指标只说明**形态**，
不等于缺陷。分诊后本仓 100 条"每条断言都弱"的测试里真缺陷只有 2 条 ——
**别把形态统计直接当发现清单**。

### 4.6 实跑取证

静态分析能给出假设，给不出结论。**纸面看不出、实跑一验即穿**是本轮 6 条 P1 的共同特征。

取证纪律：

- **带请求日志与字节级校验**，不是"跑一下看看结果对不对"。
- **计数与判分指纹逐字节比对**，确认改动前后指纹相同才算"判分影响为零"。
- 复制品执行的可信度要自证：本仓曾因 traceback 把副本路径显示成真仓路径而
  证据存疑，处置办法是在副本里插唯一标记并制造失败，确认报出的路径与标记
  都来自副本（`temp/AUDIT-A6-evals-gates.md` §"证据链有效性自查"）。
- 涉及判定器的注入要**分步**：先注入真实失败（确认会红），再叠加恒真化
  （确认可被掰绿）。只做第二步无法区分"门禁没抓"和"门禁抓了但被别处抵消"。

## 5. 四档证据等级

写任何结论时标注证据强度。**混写档位等于伪造精度。**

| 标记 | 含义 | 约束 |
|---|---|---|
| 【实跑】 | 本轮真实执行，附命令与 exit code | 可作修复依据 |
| 【入库快照】 | 结论落在已入库产物上（快照、报告、契约） | 可作修复依据 |
| 【临时实跑】 | 在 `temp/`/副本里跑出来的，产物不入库 | 可支撑方向，**数字不能写成精确事实** |
| 【未取证】 | 怀疑成立但没验 | **不得作为修复依据**，也不等于"已确认不存在" |

两条从教训里长出来的硬规则：

- **"未取证" ≠ "已确认不存在"。** 本仓 `grater` 一例：白名单依据是行数行为
  （`grater` min15 出 0 行、`greaterequal` 出 1559 行），而**站点表单下拉里到底
  有没有 `grater` 从未取证**。订正时必须如实标注未取证部分，不能顺手造一个新的
  绝对化断言顶替旧的。
- **临时实跑的数字不能写成精确事实。** `ps1` 分型那次的教训：三个采样天区的
  非空行数是 128 / 0 / 0，**两个恰好为 0** 才让"ps1 精准下载 0 行"这个错结论
  "看起来对" —— 而它危险恰恰在这里。位置相关的结论必须带 `position-dependent`
  标签，不能写成全局属性。

**统计也要标口径。**自述条目数与独立复核条目数要分开列。本仓注释审计里
"订正类提交自述约 90 条"与"独立钉住提交号并逐条复核的 16 例"差距悬殊 ——
**这个差距本身就是结论**（检出率高不等于复核率高）。

## 6. 并行协作纪律

多 agent 同仓写同一批文件时：

- **文件归属互斥。** 撞车时**先读当前工作区做增量**，不要按自己记忆里的旧版本覆盖。
- **临时产物只进 `temp/`**，永久资产进既有目录（铁律 3）。
- **分批落盘。** 连续多轮审计里出现过 agent 在"干完活正要写报告时"断线、
  全部产出丢失的情况。**每完成一个批次就落盘**，不要攒到最后一次写。
- **越界要明确申报**，不闷头改别人的文件。发现需要动别人的地盘时，
  在报告里点名"这需要 X 单批准"。
- **落盘冲突要留声明。** 出现覆盖时，把被覆盖的版本备份到 `temp/` 并在报告开头
  写明"本文件为原始产出，并行实例版本已备份至 X，未删除、未合并"——
  越权处置他人产物是更严重的问题。
- **被并发 writer 抢先提交时，核实它改对了再接受。** 实例（`temp/FIX-K1-mcp-registry.md`
  K1-04）：E5 报告已被并发 agent 重生成，处置不是覆盖，而是先在 HEAD 纯净快照上
  独立复现（`git archive` + 跑批 + `git diff --no-index`），确认
  "指标逐字一致、仅时间戳不同"后才没覆盖，并补了指标值守护。
  另一例（`2c47539`）：并发改动把 `test_e3.py` 回滚到旧版而 `items.yaml` 是新版，
  导致 `assert 10 == 7` 失败 —— **先证伪"是我注入的"再下结论**。

## 7. 失败方向与噪声源

**假红比假绿更危险。**假绿只是漏掉一个缺陷；假红是狼来了 —— 红几次没人信之后，
整道门禁会被整体关掉，那才是真的 fail-open。

审任何门禁都要问：**它红了，是因为被测对象有问题吗？**

已实测的假红来源（`temp/DETECT-E2-failure-direction.md`）：

- **环境产物**：装了 `.venv` 之后 `verify_no_version_keys` 因第三方包自带的
  `version:` 键转红 —— 与本仓源码毫无关系。
- **缺目录**：`comment_audit` 早期版本往 `temp/` 写产物但不 `makedirs`，
  fresh clone（`temp/` 不存在）必崩。红的理由是"环境缺目录"而不是"注释有问题"。
  修法一行 `os.makedirs(os.path.dirname(OUT), exist_ok=True)`
  （现见 `ops/audit/comment_audit.py:619`，注释里点名了这条判据审计的来源）。
- **真导入被测代码**：门禁 `import` 被测模块，等于执行它。模块在 import 期读
  环境变量，缺一个变量就被报成 `[IMPORT] ... KeyError`。
  **报错要分类**（缺依赖 / 缺环境变量 / 语法错 / 真断链），否则人看到
  `[IMPORT] ... KeyError` 会去查 import 语句 —— 而语句本身没问题。
- **依赖未装**：用 `python -S` 模拟裁剪克隆，三条门禁立刻因 `No module named 'yaml'` 转红。

**噪声源迟早被整体关掉，判据宁可收窄。**具体做法：

- 判据**收窄到不会误伤数据键**。全仓扫描时用**键自身的形状判据**而不是又一份文件名单 ——
  否则 `E_BACKEND` / `PENDING` / `INFO` / `SIGNED` 这类大写数据字典键会被一并收进来
  （`ops/audit/verify_crossrefs.py:310-312` 的形态 d 判据是范例）。
- **收窄级测试要写进单测**：判据过宽 → 噪声源 → 被集体关掉。
  `test_counting_claims_gate.py` 的 `test_non_assertive_forms_are_not_flagged`（L133，
  参数化 3 例）就是守这一条的。
- **扫描面用黑名单不用白名单。** 白名单的缺口只能靠不断补（`agents/` 一出现就漏检），
  黑名单的排除项是有限且稳定的。四份抄件收敛为 `ops/audit/scan_roots.py` 单一定义，
  即 `6786359`。
- **报告型工具与硬门禁分开。** 报告型工具刻意不阻断，因为它们需要人判读
  （合法清理重复定义会被 `verify_no_code_loss` 报成 token 减少）。
  但要防"报告型被人当门禁引用"，也要防"报告型被改成 exit 1 冒充硬门禁"。

### 与之配套的一条：门禁红了，先确认它指的是不是 HEAD

`ops/audit/code_fingerprint.py check` 的 **exit 1 含义是"有尚未提交的真代码改动"**，
不是"代码有问题"（纯注释/docstring 改动不算）。它在合法改动时必然触发，
提交后归零。**绝不要为了让这条门绿而改判定逻辑或回退正当改动** ——
那才是真把门禁变成摆设。同理，它只报"代码真变了"，**看不见未跟踪文件**：
磁盘上存在且未被 `.gitignore` 忽略的新文件必须 `git add`（铁律 8），
那是 `test/unit/meta/test_gate_blindspots.py::TestGitTrackingCoverage` 的职责。
两条门各管一头。
