## 1. 写"为什么"还是"是什么"

**唯一判据：把这条注释删掉，读者会损失什么？损失≈0 → 复述型噪声，删掉。**

| 该写（解释"为什么"） | 不该写（复述"是什么"） |
|---|---|
| `否则` / `刻意` / `实测` / `fail-closed` 级别的**理由** | `# 定义变量 x`、`# 调用客户端` |
| "旧实现在此出错"的历史教训 | 与同函数 docstring 逐字重复的行尾注 |
| 覆盖不到的形态要**明说覆盖不到** | 给数据行（星表列名表、指标表）逐行写右注 |

复述型注释**不是无害的**，三宗罪：

1. **占位**：稀释真信号，读者要自己筛哪些值得读；
2. **会腐烂**：它跟着代码走，改代码的人看不见它（§5 的机理），腐烂后还在占位；
3. **与谎报型共处一文件**：被独立复核的谎报型 P0 里，`src/tap/jobs.py` 一个文件就占了
   **3 条**（读函数上的"写终态"、从未落库的执行计划、不存在的时间窗配额），
   而同一文件同时是复述型噪声的聚集地 —— 也就是说**格式门禁全绿时两类问题并存**。

**别把密度指标当目标**：`comment_audit` 管的是"够不够"，本节管的是"值不值"。
写满行尾注释让对照率达标、用复述充数，是把门禁当 KPI —— 那会把门禁变成摆设。

## 2. 硬性规则（常驻部分）

> 以下 1–9 条是**常驻规范**，任何时候改代码/补注释都适用。
> 10–11 条是**"补注释专项作业"期间**的临时纪律（见 §2.2），做完即失效。

### 2.1 目标

为 `astro-best` 的 Python 代码补齐**中文注释**，使不懂英文的人工复核者能独立读懂每一个函数、
每一次外部调用、每一个 import 的用途。**只改注释，不改代码。**

### 2.2 硬性规则

1. **注释与 docstring 一律中文**（简体）。技术标识符、HTTP 路径、列名、异常类名、
   环境变量名、协议关键字保持英文原样，不翻译。
2. **禁止改动任何代码**：不改标识符、不改逻辑、不改语句顺序、不增删参数、不改默认值、
   不改字符串字面量（错误信息/消息是运行时契约，翻译会破坏测试与调用方）。
   只允许：新增/改写 `#` 注释、改写 docstring、在 import 区加注释、调整空行。
3. **保留文件头部既有结构**：`能力边界:` / `白盒锚点:` / `【权威学术来源锚定】` 等既有
   中文头注释一行不许删；若同文件存在英文 docstring，把其中文本内容改写为中文。
4. **函数/方法/类必须有中文 docstring**。保留 Google 风格小节标题
   （`Args:` / `Returns:` / `Raises:` / `Yields:`），但小节内的描述文字用中文。
   已经很好的中文 docstring 不要重写。
5. **import 必须加中文注释**。按来源分组并加分组说明：
   - 标准库组：说明用途（如 `# 标准库: 原子写与路径锚定`）
   - 第三方组：说明用途（如 `# 第三方: requests 会话 + urllib3 重试策略`）
   - 本地 `src.*` 组：说明跨了哪条能力边界（如 `# 本地: 协议层权威键集 (Q-01/05)`）
   同一 `from x import (...)` 块在块上方加一条中文注释即可，不必每行都加；
   但**单独一行的重要 import**（如延迟导入打破循环）必须单独注释说明原因。
6. **每一次外部 API / IO 调用点加中文行内注释**，说明：
   - 调的是什么（哪个端点/哪个文件/哪个系统调用）
   - 为什么在这里调（协议阶段、失败语义、降级策略）
   典型点：`requests`/`session.get|post`、`open(...)`、`os.replace`、`subprocess`、
   `Path.mkdir/unlink`、astropy/`fits` 写入、yaml 读取等。
7. **不留悬空注释**：注释必须解释"为什么"或"是什么"，不写 `# 定义变量 x` 这类复述代码的话。
   已有的高质量中文注释不要动。
8. **禁止出现版本号**（全仓铁律）：注释里不写具体版本数字。
9. **必须通过** `python -m ruff check <files>`；行宽遵循仓库现有配置。

**补注释专项作业期间追加**（做完即失效，不要写进常驻流程）：

10. 不要执行 git 命令、不要提交、不要新建或删除文件（除分配给你的文件外）。
11. 不要运行 pytest（由主控统一跑）；改完后可用
    `python -c "import ast,sys; ast.parse(open(f,encoding='utf-8').read())"` 自查语法。

### 2.3 注释密度要求

- 每个函数：1 段中文 docstring（含契约/失败语义/回归锚点，如适用）。
- 每个非平凡分支/循环/ try-except：至少 1 行中文说明其存在理由（尤其是
  "旧实现在此出错"的历史教训，务必写清，这是复核者最需要的信息）。
- 每个模块级常量/表：1 行中文说明权威来源与消费方。

**本条与 §1 的关系**：密度是**下限**不是上限。"至少 1 行"说的是**存在理由**必须写出来，
不是给每行都补一句；上限由 §1 的"删掉损失≈0 就删"把住。

### 2.4 专项作业的交付物

改动文件清单 + 每个文件新增/改写的注释条数 + 任何你发现但**未改动**的可疑之处
（只报告，不动手）。**"发现但不改"必须显式列出来** —— 静默放过一条谎报注释，
等于把它交给下一个读者。

## 3. 六类腐烂与频次（来自 git 历史实测）

样本 = 本仓 16 例钉住提交号的独立复核实例（频次只对这 16 例成立，见 §10 局限）。

| 类 | 频次 | 特征 | 可判定的筛法 |
|---|---|---|---|
| **A 行为谎报** | **5** | 注释说做了 X，代码没做 X | 词法筛 `写/落库/持久化/提交/发出/计入/统计/保证/全部/唯一/等价/同口径`，逐条判读"那一行真做了吗" |
| **C 陈旧锚点** | **4** | 引用了已搬走/已改名/已换形态的东西 | 重构后 `git grep -n '<旧符号名>' HEAD` + `git diff <sha>^ <sha> --name-status --diff-filter=R` |
| **B 契约谎报**（反向） | **3** | 注释描述的是**门禁判据**，代码恒真或判据缺席 | 注释里出现「必须/应当 → 则」判定式，去 `test/` 找钉它的断言；找不到 = 恒绿 |

## 4. 最重要的一条：谎报注释会诱导人写出 bug

> **注释腐烂的杀伤力不在"过期"，在"它自信地描述了一个不存在的行为"。**
>
> 过期注释只误导阅读；**谎报注释会诱导人写出 bug，或让人放过一个 bug**。
> A + B 合计 8 例 = 50%，全是 P0 —— 这不是巧合，是"描述性断言"的固有风险。

### 4.1 照注释"补实现"之前，先判断：实现它会不会更糟

**这是本仓最贵的一条纪律。** 注释与代码矛盾时，**默认怀疑代码，逐一裁定，不得直接动手**。

判据（二选一，必须写出理由）：

- 注释描述的是**契约/判据**，且有外部依据（协议要求、门禁要求、实测）
  → **改代码**去兑现契约。
- 注释只是**对现状的描述**，且外部依据不足
  → **改注释**，并把"它其实不是这样"写成本地可见的事实。

**实例（本仓最锋利的一条）**：`src/tap/jobs.py:213` 的读函数上挂着 `# 写终态`。
照字面"补实现"——让 `get_job` 去写终态——会与 `_transition` 的 CAS 唯一写入口**双写**，
竞态下把**已 ABORT 的作业改回 COMPLETED**。而这正是同文件 `_transition` docstring
（`src/tap/jobs.py:368` 附近）明说要防的事。**"补实现"本身是那个 bug。**

> 由此推出一条**注释写法**要求：模块/函数 docstring 里的**不变量**要写成
> **可被引用的形式**（"相位迁移的唯一写入口是 `_transition`"），
> 这样后来者读到矛盾注释时能顺着不变量反查，而不是顺着注释去改代码。

### 4.2 反向陷阱：不要只改注释

`407b795` 的 7 处里**注释是对的、代码烂了**。只改注释会把恒绿的门禁继续留着。
分流判据见 §4.1；该次提交的做法可直接沿用：**逐条独立复核后再决定改哪边**
（结果是 16 条改注释、1 条改实现）。

## 5. C 类为什么 diff 抓不到

**"改代码时忘了改注释"的机制不是人忘了，是那行注释根本没出现在 diff 里。**

| 形态 | 实例 | 说明 |
|---|---|---|
| 抄了旧数字写进新文件 | `88792e1` | 提交标题就是「client.py 463 → 380 净行」，**同一提交**新建的 `src/client_phase1.py` 模块 docstring 却写「client.py 实测 463 净行仍超 400 预算」—— 不是忘了改，是抄了旧数字，而抄的那行恰好在被改对象上 |
| 代码加依赖，docstring 的"完整清单"没加 | `1893cfd` | 清单漏一项；**清单的价值就在于完整** |
| 代码搬了家，指向旧家的注释原地不动 | `1ee56d7` | 被点名的那两个文件**在这次重构里一行没动** |

**推论（必须记住的一条）**：任何以"本次改动的 diff"为输入的检查 ——
ruff、code review、`comment_audit`、`code_fingerprint` —— **在原理上抓不到 C 类**。
C 类只能靠**跨提交复核**（下面四步），这也是它频次排到第二的原因。

### 5.1 重构提交后的四步复核（不可省）

```powershell
# 1) 这次搬家/改名动了哪些符号
git diff <sha>^ <sha> --name-status --diff-filter=R
# 2) 全仓谁还在引用旧符号 —— 命中的注释就是没跟着改的
git grep -n '<旧符号名>' HEAD -- '*.py' '*.md'
# 3) 若提交声称改了行数/规模，用本仓自己的口径复核真实值
python ops/audit/count_code_lines.py
# 4) 计数型断言交给门禁复核（见 §6）
python ops/audit/verify_counting_claims.py
```

第 3 步的必要性已被实测证明：`88792e1` 那一例正是靠它证伪了「463 净行」
（工具实测 380，400 预算其实已满足）。

## 6. 计数型断言必须挂门禁

**规则：注释里写了可机械复算的数字，就必须有门禁能重算它。登记了但没设防的坑等于没登记。**

本仓已建成 `ops/audit/verify_counting_claims.py`（已接入 `make audit`，见 `Makefile:105`）：
扫 `.py` 注释/docstring 里形如「某文件 N 净行」的断言，用 `count_code_lines.measure`
**以同一份口径**重算，不一致即判红。它的存在理由就是 §5 那一类"抄旧数字"。

三条**已知的判据边界**（写计数型注释时必须知道，否则会指望一门它管不到的守护）：

- **只查 `.py`，不查 Markdown。** Markdown 里的计数**没有任何门禁**，
  写的时候只能靠自己 + 复核者。因此：**Markdown 里的数字要少写，或写"见 SSOT"**。
- **只收口径唯一的"净行"**；「物理行」口径不统一（`splitlines()` 与"末尾换行算一行"差 1），
  刻意不收；裸计数（"26 条""共 96 列"）多指向**仓外**站点事实，无法重算，不收。
- **历史/转场语境的数字不收**（"拆分前 463""当时 581"）—— 拿当前磁盘去比它必然不符，
  而那正是它本来的用途。**所以要区分**："client.py 现在 380 净行"要挂门禁；
  "client.py 拆分前 463 净行"是合法陈述，但**不得**被读成现状。

**写法要求**：计数型断言**紧邻被数的定义**，不要散落在文件另一端的 docstring 里 ——
`README.md` §7 已把「注释里不写会腐化的裸数量，要写就紧邻被数的定义」列为硬要求。

## 7. 门禁注释的特殊风险

> **门禁的注释/文档若描述了它做不到的事，那是 P0** ——
> **门禁绿了会让人以为某事被守住了**，那比没有门禁更危险（fail-open 方向）。

**规则：门禁的"宣称"必须逐字落在它真正做到的事上。宣称要窄，判据可以少。**

| 坏形态 | 后果 |
|---|---|
| 宣称"找出**全部** X"，而判据只覆盖 X 的一部分形态 | 读者以为新缝一落盘就被守住 |
| 宣称"守得住 Y"，而 Y 的一个子类实际不查 | 正好漏在它自称要守的那一类退化上 |
| 判据描述里带"必须/应当 → 则"，但 `test/` 里没有断言钉它 | 该条判据恒绿 |

**真实实例**：`test/unit/meta/test_gate_blindspots.py` 的委派缝门禁曾宣称
"从 AST 找出**全部**纯转发壳，新缝一落盘就被纳入覆盖"，而判据只校验关键字实参的
**名**、**丢弃值** —— 恰好漏掉它自己点名的"静默查错天区"那类退化。
（全扫描面内关键字转发的函数型缝实测 0 条，故当时**无活受害缝**，属潜伏缺口。）

**本仓已有的正确修法（照这个写）**：把 docstring 改成**两份清单** ——
「守得住的 N 种退化」+「守不住的 M 种形态（并写明为什么不查：判据刻意不猜意图，
宁可漏报也不报无法整改的红）」，段首再写一句「**被扫到 ≠ 每种退化都被守住**」。
该门禁现在就是这么写的（`test/unit/meta/test_gate_blindspots.py:546` 附近），
**收窄宣称本身就是合格交付**，不必非要把判据补全。

**另一条同源纪律**：门禁判据数量变了（`comment_audit.py` 历经十三类 → 十四类 → 十五类），
**门禁自己的注释也要跟着改** ——
本仓曾出现 `comment_audit.py` 的模块 docstring 仍写「十三类/十四类」，
而 `comment_audit` 管的是"注释够不够"、**查不了数字断言**，于是这处腐烂长期无人报警。
数字型腐烂的兜底只有两种：**挂门禁**（§6）或**收窄宣称**（本节）。

## 8. 优先核这四种形态

代价最低、命中率最高的四种形态，改完代码**先查这四类**：

1. **否定式断言**：「仅」「只」「绝不」「不」「唯一」「必须」—— 否定比肯定更容易在
   后加的例外里悄悄失效，且没有任何工具会提醒你。真实例：注释写"六个出网请求点的
   **唯一**取值口"，而 `check_connection` 的连通性探测**刻意写死 30s 独立超时**
   不经该属性 —— 属性一写下就与它冲突（`src/client.py:181` 附近的 `request_timeout`）。
   订正写法：把"唯一"改成"**主要**"，并**点名那个例外及其理由**。
2. **唯一性承诺**：「X 由 Y 唯一决定」「唯一取值口」「唯一写入口」—— 同上，且否定式里最重的一档。
3. **单点外推**：「实证 / 实跑 / live」**必须同时写采样点或样本量**；
   没有就降级标注。推广前先问一句：**这个结论是在几个采样点上测的？**
   （D 类三个采样点里两个恰好为 0，所以它"在多数天区看起来对"—— 这正是它危险的原因。）
4. **枚举与计数**：中文数词最易写飘（不像阿拉伯数字能被 grep 核对），
   写完当场数一遍同段条目数（E 类两例的共同成因）。

## 10. 口径来源与复算

**数据来源**：本仓全量 `git log -p` 翻查（审计时 HEAD `ce0a144` 的 76 个提交），
逐条 `git show` 复核注释原文与代码行为，独立钉住提交号并复核过的实例 16 例（P0 9 例）。

提交号入库** —— 每条实例都能用 `git show <sha>` 独立复核，不依赖那份报告存在。

**复算命令**：


**必须一起记住的局限（不要外推）**：

1. **16 例不是全仓腐烂率**。它们来自"已被检出"的那个池子，存在**幸存者偏差** ——
   烂得更久、更隐蔽的注释只会让这个分布显得更乐观。
2. **半衰期 22 个提交是被检测频率决定的**，不是腐烂速度的真实度量。

3. **本仓注释审计的误报率与检出率同量级**（检出侧 47 条断言中 14 条不符 = 29.8%；

4. 六类频次只对这 16 例成立；**排序（谁更危险）可外推，比例不可外推**。
