# 工程踩坑登记册（astro-best）

> **为什么要有这份文档**：注释只描述「现在这段代码怎么工作」。踩过的坑、改动的
> 来龙去脉、尚未兑现的声明属于**过程知识**——放进注释里，注释会随时间越来越难读，
> 读代码的人也分不清「这是现状」还是「这是历史」。故集中登记于此。
>
> **收录标准**（三条都满足才收）：
> 1. 当时真的错了、真的踩了，且现象隐蔽（不是一眼能看出的报错）；
> 2. 现在有护栏，或至少有一句明确的现状声明；
> 3. 不查这份文档就一定会重犯。
>
> **与其它文档的分工**（别往这里塞别的东西）：

## A. 门禁本体：判据写错比没判据更贵

### A-1 行尾注释判据写反，第一次整改整体做反了方向

**现象**：`ops/audit/comment_audit.py` 的 Q7 最初把「COMMENT token 的起始列 > 0」当行尾。
函数体里顶在代码上方的 `    # 说明` 恰好满足 `col > 0`，于是**任何缩进的独立注释行
都被算成行尾**。

**为什么贵**：这个错判据不是让门禁变松，而是让它**可以被"保持缩进"一路刷高**——
而那恰恰是本仓要反对的形态。首版按它整改后 71 个文件"达标"；改用严格口径复测，
**154/226 个文件的真实行尾注释为 0**。整改方向整个反了，白做。

**现在的护栏**：判据是「同一行 `#` 左侧有代码」（`lines[行号-1][:起始列].strip()`
非空），由 `test/unit/meta/test_audit_gate_contracts.py::TestTrailingCommentCriterion`
的反例样本钉死。

**通用教训**：写指标类判据时，先问「**这个指标能不能被规避动作刷高**」。凡是
「保持某种写法就能让指标变好」的指标，都是在给自己造假绿。

### A-2 「代码零丢失」护栏自己错过三次

**现象**：`ops/audit/verify_no_code_loss.py` 用来证明"这轮只改了注释、没删代码"，但它自己
错过过三次：

1. 给函数补 docstring 时，docstring 被替换成 `Pass` 节点 → 误判为代码变更；
2. `[Pass]` 与 `[]`（函数体只有 docstring 时剥离后）不同形 → 同样误判；
3. （第三次的细节见 `file-size-budget.md` §4.5 的踩坑记录。）

**为什么贵**：护栏一旦误报，人就会开始忽略它；一旦漏报，它给的安全感是假的。
两次都是"补 docstring"这个**最无害**的动作被判成代码变更。

### A-3 恒返回 0 且什么都没比的门禁，比没有门禁更危险

**现象**：`ops/audit/code_fingerprint.py` 曾把 git 仓根硬编码成父目录 `<SKILLS_ROOT>`，
而本仓是独立 git root。`git show HEAD:...` 恒 exit 128，全部文件落进"新增未跟踪"
分支，`compared` 恒为 **0**——工具"比对过 0 个文件"却照样 exit 0，在 `make audit` /
`make check` / `make all` 里显示为通过。

**现在的护栏**：`test/unit/meta/test_audit_gate_contracts.py` 断言 `compared > 0` 且
`compared == in_head`（反 fail-open）。

**通用教训**：门禁的"通过"必须能被区分为「查过了且没问题」与「没查到」。**区分的
最省事办法是把"查了多少"也报出来**（`print(f"扫描 {scanned} 个文件")`），并对它
设一条 `> 0` 的断言。

### A-4 判据清单写在两处，概数从「七类」漂到「十一类」

**现象**：Q10 的十一类排除口径，清单写在 `analyse_line_alignment` 的 docstring 里，
调用点上方又有一份注释。两处都写着过时的概数——docstring 写「七类」，末尾还残留
一条「三类不算」——而实现早已扩到十一类。

**现在的处置**：清单收敛到 `ops/audit/line_scope.py` 的模块头（一张表），
`nontrivial_stmt_rows()` 是分母的唯一来源；`ops/audit/comment_audit.py` 侧只指向它。
并由 `temp/split_equivalence.py` 对拍证明拆分**只搬不改**（255 文件 / 4092 分母行
零不一致）。

**通用教训**：**清单与实现在同一个函数里就已经会漂，跨文件只会漂得更快。**
凡是"列举 N 项"的地方，要么让实现从清单生成，要么只留一份。

## B. 拆分与迁移：搬代码不等于搬对了

### B-1 搬判据本体时多删一行，吃掉两处 `return`

**现象**：把 Q10 的行分类层从 `ops/audit/comment_audit.py` 搬进 `ops/audit/line_scope.py`，迁移脚本按
AST 取 `end_lineno` 后多删了一行"块后空行"。实际那两行是**真代码**——
`analyse_trailing_style` 与 `analyse_comments` 的 `return findings` 被吃掉，
运行期表现为 `'NoneType' object is not iterable`。

**怎么发现的**：不是肉眼 diff，是两道机械检查——
(a) `ruff` 的 `RET503`（缺显式 return）与 `F821`（未定义名）；
(b) 一条"标注返回非 None 却没有 return 值"的 AST 自查。

**通用教训**：搬判据本体这类"错了仍能跑"的内容，**先备好机械检查再动手**：
`RET503`/`F821` + 一条 AST 自查，比任何 review 都可靠。

### B-2 `Path.write_text` 在 Windows 上把 LF 写成 CRLF

**现象**：迁移脚本用 `Path.write_text(..., encoding="utf-8")` 写文件。文本模式下
Windows 会把 `\n` 翻译成 `\r\n`，于是写出来的两个文件带着 CRLF 进了仓，
而本仓行尾铁律是 LF。

**怎么发现的**：并行批次跑 `ops/audit/check_line_endings.py` 时报出 2 个 CRLF 文件。

**通用教训**：Windows 上写仓内文件**一律走 `write_bytes()`**，或
`open(..., newline="")`。用 `write_text` 写代码文件是本仓的固定陷阱。

### B-3 门禁工具用包路径导入，直跑时 ModuleNotFoundError

**现象**：拆分方案原本写 `from ops.audit.line_scope import ...`。但
`ops/audit/comment_audit.py` 既可能被 `python ops/audit/comment_audit.py` 直跑（此时
`sys.path[0]` 是 `ops/audit/`，仓根不在 path 上），也可能被单测注入 `ops/audit`
后 `import comment_audit` 拉起。包路径在前一种场景直接崩。

**现在的处置**：同目录裸名 `from line_scope import ...`，两种场景都成立。

### B-4 拆文件前没 grep 覆盖矩阵锚点

**现象**：覆盖矩阵有 AST 硬校验（文件 + 类 + 方法必须存在），拆文件会让锚点失效，
门禁当场红。**教训：拆文件前先 grep 覆盖矩阵锚点，把锚点更新列入同一改动。**
（详见 `governance-debt-plan.md` §12.2。）

## C. 数据正确性：静默损坏比崩溃贵

这一类的共同形态：**旧行为不报错，只是把数据悄悄弄错**。所以判据必须是
「不变量 + 后果」的陈述，而不是"以前出过事"。

### C-1 CSV 消毒内联复写，把合法负数损坏掉

**现象**：首字符消毒判定（`v[0] in ("=", "+", "-", "@")`）曾被内联复写进多个落盘
路径。CSV 注入防护对 `-` 的处理会把**合法负数字符串**损坏掉——南天的
`dec = "-5.0"` 会被写成 `"'-5.0"`。且四个导出器里有两个根本没接消毒。

**现在的护栏**：`src/csv_safety.py` 是全包唯一实现（`sanitize_row` /
`sanitize_cell`），各 emitter 必须接；`test/unit/serialization/test_output_formats.py`
钉住"不误伤合法负数"。

### C-2 非白名单输出格式按 JSON 写却拿值当扩展名

**现象**：`output_format` 只对 `"csv"` 走 `to_csv`，其余值一律按 JSON 写，
却把该值原样当文件扩展名。`output_format="txt"` 会落一个 **`.txt` 里装 JSON** 的
文件，下游按扩展名分派解析器时静默解析失败。

**现在的护栏**：白名单只 `csv` / `json`，其余显式抛 `ValueError`（`P2-11` 同款
"显式失败"纪律）。

### C-3 表头宽度按「数据行最大宽」判定，30 列表头被整列丢弃

**现象**：一行数据里有未转义逗号时会多出一列，若按"数据行最大宽"判表头，
真实表头 `h1..h29` 会被整列丢弃。

**现在的护栏**：表头权威，多余值落 `overflow_*` 键。

### C-4 哨兵值无差别套用，合法负星等被抹成 NaN

**现象**：哨兵判定一旦无差别套用到全部列，高自行星的 `pmra`（可达 ±1e4 mas/yr）
这类**合法值**会被当成缺失抹成 `None`；`-30.5` 这样的合法负星等会跟着被打成 NaN。

**现在的护栏**：哨兵判定只认 `<= -999.0`，且阈值走唯一共享件
`evals/_data/null_sentinel.yaml`（**判据与取值分离**）。

**附带的坑**：哨兵字典的静态守卫曾对**任何**负哨兵恒不命中——Python 把 `-999.0`
解析成 `UnaryOp(USub, Constant(999.0))`，而判据只认 `ast.Constant`。详见
`ops/audit/README.md`「第三轮门禁变更登记」。

### C-5 自动下载名唯一性只到「星表 + ID 数」，并行任务互相覆盖

**现象**：同星表、同 ID 数的两个并行任务会生成同名文件，经 `_save_result` 的原子写
（`os.replace`）互相覆盖。

**现在的护栏**：自动名唯一性必须细到 `job_id` 粒度。

### C-6 未知输出格式静默回落 JSON，请求 FITS 拿到 .json

**现象**：请求 `fits` 的调用方拿到的是 `.json` 文件，扩展名与内容互相矛盾，
且**无任何提示**。

**现在的护栏**：未知格式显式抛错。

## D. 资源与并发

### D-1 `with conn` 只提交不关闭

**现象**：`sqlite3.Connection.__exit__` **只提交事务、不关闭连接**。写成
`with self._lock, self._connect() as conn:` 时每次作业操作都建连即弃，
句柄累积，`database is locked` 概率随之上升，而 `close()` 也没有任何连接可关。

**通用教训**：`with` 的语义因对象而异。**数据库连接、锁、线程池都不是"用完自动
关闭"的东西**。

### D-2 线程池 `close()` 零调用点

**现象**：job store 持有工作线程池，`close()` 没有调用点，句柄随进程悬挂。
**已修（2026-10-05 核实）**：`src/tap/jobs.py:391` 的 `close()` 走
`self._pool.shutdown(wait=False, cancel_futures=True)`，调用点在
`src/tap/service.py:523`（HTTP 服务 `server_close()` 之后的收口，
经 `getattr(server.gateway, "job_store", None)` 取，未启用异步时为空值）。
测试侧 `test/unit/tap/test_service.py`、`test_tap_robustness.py` 收尾均显式
`store.close()`。

### D-3 「先查后改」拆成两条语句，abort 与完成互相覆盖

**现象**：检查与改写分成两条语句时，竞态下会把已 ABORT 的作业写成 COMPLETED。
**现在的护栏**：把"检查 + 改写"压成一条语句（靠 SQLite 的写锁原子性）。

### D-4 客户端每次调用新建，节流时钟被整个绕过

**现象**：三个公开入口每次调用都新建 `BestClient`，`rate_limit` 时钟随之重置——
等于把节流整个绕过。「每次新建是刻意的，因为共享会让限流时钟跨调用串味」这个
说法经逐条核对**不成立**（裁决见 `file-size-budget.md` §6 A1）。

**现在的护栏**：三个入口共用同一个 `BestClient`。

## E. 协议与量纲

### E-1 角度当角秒下发，锥形检索恒空

**现象**：半径单位混用，`0.1` 度被当成 `0.1` 角秒下发，结果永远是空锥区。
**现在**：半径必须从度换算成角秒。

### E-2 ADQL 的 OR 分支无上限

**现象**：OR 分支被照单全收时，每个分支一次 HTTP，**40 个 OR 就足以把服务端打挂**。
**现在的护栏**：分支数必须有上限。
**已修（结构变更后仍在）**：`src/tap/adql.py` 的 `max_branches`（公开入口默认 16）
在**展开过程中**就掐断（`if len(branches) > self.max_branches`），
下限钳到 1（负上限等于没上限）；回归锚点
`test/unit/tap/test_adql.py`（造 40 个 OR 分支必须被拒，24 passed）。

### E-3 非法 Range 回 200 全量

**现象**：非法 Range 当成普通请求回 200 全量，客户端续传逻辑随即错乱。
**现在**：必须回 416。

### E-4 410 报成 404，误导下游重试

**现象**：作业行可查说明它本应存在、只是不可恢复，报 404 会误导下游重试。
**现在**：410 而非 404。

### E-5 分页是绝对偏移，断点漏存 `page_size` 就真丢行

**现象**：阶段 2 的 `page=N & rows=M` 不是会话内游标，而是**绝对偏移**（服务端
跳过前 `(N-1)*M` 行）。于是「页号」不是可以独立存取的量——它只在与产生它的
`rows` 同一个会话里有意义。

**实跑证据（2026-10-04，ps1 锥搜 ra=180 dec=30 r=300as，sqlid=s4943）**：
`page=1&rows=1000` 回 1000 行、`page=2&rows=1000` 回 1000 行，而
**`page=2&rows=100` 的 100 行与 `page=1&rows=1000` 的 `[100:200]` 逐行完全
相同**（`offset_semantics=true`）；同参数二次取回完全一致（`repeatable=true`）。
**逐行相同才是决定性判据**；`page1 ∩ page2` 交集为 1 行（非 0）不作为判据——
服务端无 `ORDER BY` 时行序本就不保证稳定（`site-endpoints-and-interactions.md`
§6bis 已记同族现象：同参数两次取回集合重叠仅 1/50）。
证据：`temp/LIVE-PAGING-results.json`，脚本 `temp/LIVE-PAGING.py`。

**为什么贵**：A3-01（断点续传丢行，`temp/AUDIT-A3-download.md:70`）此前把严重度
悬在「偏移 vs 游标」这个**未验证**前提上——那份报告原文写明该语义「取自代码，
未对真实站点验证」，并预留了「若站点实为会话内游标，丢行会降级为错序」的分支。
实跑把它钉死后，结论从「可能只错序」变成「**真丢行，且无重复**」。

**现在的护栏**：`src/client_paging.py` 的 `fetch_sqlid_data` 已是成对语义
（`start_page` 配 `initial_sources`）。断点结构必须与它同步——**漏存 `page_size`
就让下一段从错误的偏移起算**，且产物行数少于请求值而终态仍是 `done`。

**通用教训**：**偏移量不是位置**。凡是把「页号」单独存进断点/游标的，都要问
一句「它跟哪个分页参数绑在一起」——不同页大小下的同一页号，是两个不同的数据集。

### E-6 探针吃掉 sqlid 的 `s` 前缀，假软 404 被读成「表坏了」

**现象**：手搓裸 `requests` 探针用 `re.search(r"sqlid/s?(\d+)", text)` 取会话号
（`s?` 落在捕获组**外**），拿到裸数字就拼 `/sqlid/4956?...` 取页。站点回
**HTTP 200 + 22 B `{"error":"Not Found"}`**。而同一会话的 `getcount` 用裸数字
完全正常——于是读起来像「会话活着，但这张表/这条路死了」。

**实跑证据（2026-10-04，同一 sqlid `s4958`、同一页，唯一变量是前缀）**：

| 请求 | 字节 | 体 |
|---|---|---|
| `/sqlid/s4958?output.fmt=csv&rows=100&page=1&…` | 24997 | 真实 CSV（BOM + `inputobjs_*` + `ps1_ra`…） |
| `/sqlid/4958?output.fmt=csv&rows=100&page=1&…` | 22 | `{"error":"Not Found"}` |
| `/sqlid/4958/getcount` | 15 | `{"total":5109}` |
| `/sqlid/s4958/getcount` | 22 | `{"error":"Not Found"}` |

**两套形态且恰好相反**：取页要 `s` 前缀，`getcount` 要裸数字，写反任一个都是
22 B 软 404。证据：`temp/LIVE-SESSION-BINDING` 一类的三轮排除见下。

**被排除的假设**（别顺着这些方向查）：cookie、`X-CSRFToken`、`User-Agent`、
`Accept` **全都不是杠杆**。同一表单、同一 cookie、同一天区逐项打开头，四种组合
一律 22 B；换 `BestClient` 走同一天区立刻拿到 24997 B。
证据：`temp/LIVE-SESSION-BINDING-results.json`、`temp/LIVE-HEADER-BINDING-results.json`、
`temp/LIVE-MATRIX-results.json`（脚本同名前缀）。

**客户端为什么免疫**：`src/protocol.py::parse_sqlid` 保留 `s` 前缀，交给
`src/protocol.py::build_page_url` 拼取页 URL；只有 `count_sqlid` 才
`removeprefix("s")` 供 getcount 用。两种形态由两个函数各管一处，探针绕过它们
就必错。

**通用教训**：**看到 22 字节软 404，先怀疑自己拼的 URL**。判据很便宜：同会话
换一个端点（`getcount`）还通不通？通，就说明会话是活的，问题在地址。
（本条最初被误记成「漏 `csrfmiddlewaretoken`」，实跑三轮排除后才定位到前缀。）

### F-1 自建 `box-between` 键集，锥形检索结构性失效

**现象**：一道只做 strip 后形状检查的门禁被称作 "syntax validation"，

**现在的护栏**：注释里**禁止**把它称作 "syntax validation" 或等价说法——
**命名声称的能力必须等于实际检查的能力**。

## H. 恒真与 fail-open：看起来在检查，其实没有

这一类单独成节，因为它的形态最统一：**门禁/判据存在、能跑、退出码正常，但对它声称
要拦的那类问题一次都没命中过**。读者看到「已检查」就以为「已覆盖」。

**统一的识别法**：拿一个**明显违规**的样本喂进去，看它报不报。样本必须是现造的
（真实树干净时没有违规样本可用）。仓里这个手法叫「反证夹具」，
落点在 `test/unit/meta/test_audit_gate_contracts.py` 与各实验的 `tests/`。

### H-1 中文判定函数丢了 `return`，全仓 4572 条误报

**现象**：`ops/audit/comment_audit.py` 的 `_has_cjk()` 在一次文件迁移中只剩 docstring、
丢了 `return bool(CJK.search(text or ""))`，恒返回 `None`。于是 Q3（docstring 非中文）、
Q5（模块头非中文）、import 组中文覆盖三类检查对**每个文件无条件误报**，一度刷出
`docstring_not_chinese: 2765 / module_header_not_chinese: 256 / import_group: 1576`。

**它为什么能溜过去**：自查脚本写的是「标注返回非 `bool`/`None` 的函数必须带 return」，
把 `-> bool` 当例外排掉了——而 `_has_cjk` 正好返回 `bool`。**例外规则本身成了盲区。**

**现在的护栏**：自查不再按返回类型开例外；另抓「函数体只剩 docstring」这个更强的信号。
另有「标注返回非 None 却没有 return 值」的全仓 AST 自查（2401 个函数定义）。

### H-2 哨兵静态守卫对任何负哨兵恒不命中

**现象**：`evals/equivalence/sentinel.py` 声称扫 `<= -999` / `== -999` 这类硬编码哨兵，
判据却是 `isinstance(operand, ast.Constant) and float(operand.value) in {...}`。
而 Python 把 `-999.0` 解析成 `UnaryOp(USub, Constant(999.0))` —— **`Constant` 判定恒 False**。

**它为什么能溜过去**：旁边的 `test_no_hardcoded_sentinels` 只断言「扫出来是空的」。
真实树零违规时，守卫彻底死掉它照样绿。

**现在的护栏**：守卫侧补 `UnaryOp(USub)` 分支；测试侧加**端到端反证**——往 `evals/`
真放一个硬编码哨兵文件，守卫必须报出来（`evals/equivalence/tests/test_equivalence.py`）。

### H-3 「反证夹具自证」不进放行条件，判定器失效照样 exit 0

**现象**：`evals/groundtruth/metrics/__init__.py` 的 `metascore()` 写着
「metascore < 1.0 → E2 FAIL（判定器自身失效）」，而 `run_e2.run()` 的 `pass` 只由
「case 全过 + 无缺件」决定，metascore 仅进报告，退出码只看 `pass`。
**判定器漏抓注入故障时整轮照样绿**，报告正文却照印「必须 1.00」。

**现在的护栏**：metascore 并入 `pass` 的合取项，并由 `TestBrokenSelftest::
test_metascore_gates_the_overall_verdict` 反证（同时断言 `n_pass` 不被连带改掉，
防止有人用「改 case 判定」的方式糊掉这个洞）。

### H-4 canary 探针吞异常，「全挂」与「稳定」在指纹上同形

**现象**：`evals/repro/run_e6.py` 的 canary 探针把异常吞成 `rows = []`，而
`canary_after` 直接复用 `before`。于是「探针全挂」与「跑批稳定」在指纹上**同形**——
一条恒真的稳定性证据，比没有证据更糟。

**现在的护栏**：失败单独记进 `failed_probes`，循环结束后显式抛错阻断。
注释里也写明「探针成功时本分支不执行，判定语义与指纹值均不变」。

### H-5 未跑的模式预置 `rate=1.0`，零证据也能拿高综合分

**现象**：`evals/eval_runner.py` 把未跑模式的 `rate` 预置成 `1.0`，`evaluate_rubric`
于是把 correctness / determinism 按满分计。纯审计模式（`--mode audit`）在**零行为证据**
下也能报出高综合分，且 blocking 不触发。

**现在的护栏**：`measured` 语义——没测一律按 0 分并显式阻断
（`behavior_not_measured` / `docstring_not_measured` / `audit_not_measured`）。

### H-6 「无 findings」当满分，0% 通过率也显示 PASS

**现象**：`eval_runner` 的 docstring 维度在「无 findings」时直接给 `1.0`。
于是 0% 通过率也会显示 PASS。

**现在的护栏**：基线永远取真实通过率，findings 只做额外扣罚（每条 -0.1，下限 0），
因此不存在「恒真分支」。

### H-7 `actual` 从用例文件名反推，比较恒真

**现象**：`evals/case_executor.py` 曾从用例文件名里有没有 `violated` 反推 `actual`。
「违反用例判 blocked、通过用例判 pass」这个比较**恒真**——门禁逻辑
（`protocol.is_soft_error`）就算整个退化成「永远返回 False」，评测也永远全绿。

**现在的护栏**：`actual` 完全由生产判定函数算出，用例文件名绝不参与。

**同族形态**：只做 `hasattr` 校验也属此类——它只能证明「名字还在」，证明不了
「行为还对」，函数被改成永真/永假桩也能全绿（`EVAL-10`）。

### H-8 审计基类默认 `return True`，忘了重写就静默拿到「通过」

**现象**：`evals/audit/__init__.py` 的基类实现曾是 `return True`。新增审计器若只写了
`run()` 忘了重写本方法，就会静默拿到 True，即「反证夹具从未真正跑过检查」也被判成
审计器有效。

**现在的护栏**：基类实现改为 `raise NotImplementedError`，与同类 `run()` 同口径，
不给默认 True 这条 fail-open 退路。

### H-9 探针按错误签名调用，`TypeError` 被 `except` 吞成「显式失败」判绿

**现象**：`evals/probes.py` 曾按**实例方法**调用 classmethod `lc.from_client(None)`，
注定抛 `TypeError`；而 `TypeError` 被下面的 `except` 当成「显式失败」判绿——
这条探针于是**无论能力好坏都恒绿，零信息量**。

**通用教训**：`try/except` 把「我调错了」和「被测对象失败了」混成同一结果时，
探针就失去了证伪能力。**签名必须按真实定义走。**

### H-10 必读源内容为空时门禁零覆盖却绿灯

**现象**：`ops/audit/verify_crossrefs.py` 的 `load_yaml` 只在「读不到 / 解析失败」时记
`[YAML]` 问题；文件存在但**内容为空**时 `yaml.safe_load` 返回 `None`，它一声不吭。
于是五节 `if spec:` 之类守卫整节跳过——门禁 exit 0 而那一节的覆盖是零。

**通用教训**：**空与坏是两类问题**，混记成同一类就必然有一类漏。
同文件第 7 节早有 `else: issues.append(...)` 的正确写法，这五节只是没照做。

### H-11 指纹只算列名，行内数值漂移全部漏检

**现象**：E6 的 canary 曾只对**列名**做指纹。列名与结构完全不动、只改行内数值时，
指纹不变——数据版本门禁就瞎了。

**现在的护栏**：`canary_fingerprint` 必须指纹**整行规范化**。
同族形态：`validate_trace` 不重算 `payload_fp`，则只剩字段级校验，改嵌套值一律逃过。

## I. 注释与文档：描述与现实脱节

这一类单列，因为它的**失效方式与 A–H 全部不同**：上面各类是代码做错，
这一类是**代码一直是对的，而旁边那句描述是错的**。读代码的人被那句话引导，
于是"代码没问题"这个判断本身就建立在错误前提上。

**本节的核心结论（2026-10-05 全量翻查 76 个提交、逐条 `git show` 复核 16 例得出）**：

> **注释腐烂的杀伤力不在"过期"，在"它自信地描述了一个不存在的行为"。**
> 过期注释只误导阅读；**谎报注释会诱导人写出 bug，或让人放过 bug**。

按 16 例的分布，**A + B 两类合计 8 例（50%）且全是 P0**，C 类 4 例 100% 由重构触发。
本节各条的"可机械检测吗"一栏是本节与其它各节最大的差别：**绝大多数是"否"**——
这类坑没有任何一道门禁能自动抓住，下面逐条写清哪些挂了门禁、哪些没有。

### I-1 注释自信地描述了一个不存在的行为

**现象**：一句注释声称某处做了 X，代码里那一步压根不存在。最狠的三例都在
`src/tap/jobs.py`（详见 [I-2](#i-2) / [I-3](#i-3)），另两例是
`src/ai_tools.py` 的「重试也会被如实计入」（实跑：服务端收 3 次，本字段报 1）
与「与 `compute_data_hash` 同口径」（本函数多 `default=str`，`separators` 取 json
缺省 `", "`/`": "`，对方是紧凑 `","`/`":"`，**同一载荷摘要逐位对不上**）。

**为什么这是本仓最高频的 P0**：A 类 5 例 + B 类 3 例 = 16 例的一半，且全部会让
人做出错误技术判断。过期注释的读者会想"这函数过时了，我去查一下"；
**谎报注释的读者会直接开始改代码**。

**⚠ 显式警告：按注释补实现是危险动作。**

读代码时发现"注释说要做 X、代码没做 X"，**第一反应必须是"实现它会不会更糟"，
而不是"代码漏实现了"**。三条判据，逐条都要过：

1. **有没有反向证据表明"不做"才是对的？** `_transition` 的 docstring 明说它是
   相位迁移的**唯一写入口**——那么"读函数也写终态"就是与它双写，不是补漏。
2. **协议/契约要求它存在吗？** 执行计划落库：UWS v1.0 不要求持久化执行计划，
   **加列是没有协议依据的 schema 迁移**。
3. **注释描述的是"现状"还是"契约"？** 描述现状而依据不足 → 改注释；
   描述契约且有外部依据（协议要求 / 门禁要求 / 实测）→ **改代码**。
   `407b795` 的 7 处全是后者，注释一字未动。

**可机械检测吗**：**否**。只能靠人工判读。可用的**筛法**（词法扫描，命中即人工核）
取自本仓实例——描述副作用与绝对量的词命中密度远高于普通注释：

```
写 / 落库 / 持久化 / 提交 / 发送 / 发出 / 计入 / 统计 / 保证 / 一定 / 全部 / 唯一 / 等价 / 同口径 / 不会 / 绝不
```

**通用教训**：**注释与代码冲突时，先假设注释错。** 这不是谦辞，是成本判断——
错注释会被下一个人当成需求实现，而那通常是竞态或无依据的 schema 变更。

### I-2 读函数上写「写终态」，照它实现就与 CAS 唯一写入口双写

**现象**：`src/tap/jobs.py` 的 `get_job` 上一行曾写着 `# 写终态`，
紧接着是 `with self._db() as conn:` 与一条纯 `SELECT`——**一行都不写**。

**为什么贵**：按这条注释"实现"（让读函数写终态）会与 `_transition` 的 CAS
唯一写入口**双写**，竞态下把已 ABORT 的作业改回 COMPLETED。
**那正是 `_transition` docstring 明说要防的事**——注释会诱导人写出它要防的 bug。

**现状**：`# 纯读: 相位迁移的唯一写入口是 _transition`。

**可机械检测吗**：**否**。可借 `verify_doc_consistency` 的 DEADPARAM 判据
（docstring 声明而函数体零引用）作近似，但本例是**行内注释**、且声称的是
"做了 X"而非"用了 Y"，那道门禁不覆盖。

### I-3 声称「落库」与「配额按时间窗」：两处都指向不存在的机制

**现象**（两条都在 `src/tap/jobs.py`，均已订正）：

| 当时的注释 | 代码事实 | 照它实现的后果 |
|---|---|---|
| `plan,  # 把执行计划整体落库` | `tap_jobs` 表**无 plan 列**；两处写库白名单都不含 plan；`src/tap/` 全目录无 plan 写入点 | **无协议依据的 schema 迁移**（UWS v1.0 不要求） |
| `... # 配额按时间窗统计, 不靠内存计数` | 该位置挂在重启收敛 UPDATE 的 `updated_at` 上；配额 SQL **无任何时间谓词**，`created_at` 从不出现在 WHERE 里 | **加上时间窗会削弱配额** |

**怎么查的（这条方法可复用）**：第一例查了**三个方向**才敢下结论——
表里没这列 / 两处写表白名单都排除 / 全仓无写入点。**只查一个方向就宣布
"注释说谎"是不够的**：schema 可能有别的路径在写，白名单可能只是漏了。

**现状**：第一条改为显式声明"只在本调用内用, 不落库 (`tap_jobs` 无 plan 列)"；
第二条**整条删除**（理由写进提交：加时间窗反而会削弱配额）。

**可机械检测吗**：**否**。但第一例的"三方向"是机械的，未来可做成
「注释里的落库声明 vs 全仓写入点」的比对工具；本轮未建。

### I-4 陈旧锚点的 diff 特征是「这次提交没碰它」

**现象**：注释引用了已搬走 / 已改名 / 已改形态的东西。**4 例 100% 由重构触发**，
不是人忘了改。

最典型的一个是**抄了旧数字写进新文件**：`88792e1` 的提交标题就是
「`client.py` 463 -> 380 净行」，同一提交**新建**的 `src/client_phase1.py`
模块 docstring 却写「`client.py` 实测 463 净行仍超 400 预算」——
提交把 client.py 降到 380 的**同时**，新建文件说它还是 463 且仍超预算。
用本仓自己的 `count_code_lines` 复核实测 380：**463 当时就是错的，且 400 预算
其实已满足**。

**为什么 ruff 与 code review 都看不见（这条是机制，不是现象）**：

> 注释腐烂的 diff 特征是**"这次提交没碰它"**。文件在这次重构里一行没动，
> 那行注释就根本不出现在 diff 中。因此**任何以"本次改动的 diff"为输入的检查
> （ruff、code review、`comment_audit`）在原理上抓不到 C 类**。

**可机械检测吗**：**部分**——已挂 `ops/audit/verify_counting_claims.py`
（`make audit` 第九道硬门禁，2026-10-05 建）。它抓的是
「`<旧名>.py` … `<N> 行`」这一形态，**只查 `.py` 里的断言、不查 Markdown**，
且**刻意不收**历史语境（「拆分前 463」说的就是过去）、裸计数
（「26 条」多数指向仓外站点事实）、口径不唯一的形态（物理行 vs 净行）。
**这就是为什么 C 类仍然需要人工跨提交复核**——门禁只覆盖了"计数型锚点"这一种。

**通用教训**：**重构提交要额外带一次"旧符号名"的全仓 grep**：

```
git diff <sha>^ <sha> --name-status --diff-filter=R   # 找出被改名/搬家/删除的符号
git grep -n '<旧符号名>' <sha> -- '*.py' '*.md'        # 看引用它的注释跟没跟着改
```

### I-5 单点实测外推成全局属性；清理不完整本身就是一种腐烂

**现象**：`ps1_source_id` 被写成「线上逐行为空（live 实证）」，而该结论**只在
一个天区测过**。三次实跑（同一语句只换天区，r=600″/300 行）非空行数：

| 天区 | 非空 |
|---|---|
| (286.1, 15.7) | **128/300** |
| (180.0, 30.0) | 0/300 |
| (10.68, 41.27) | 0/300 |

**为什么最危险**：三个采样点里**两个恰好为 0**，所以它在多数天区"看起来对"——
**看起来对正是它能活 65 个提交的原因**。

**两次腐烂叠加**（这是本条比"结论错了"更值得记的部分）：一次单点观测
污染了 **3 份文件**（`references/` + `rag/knowledge/` 两条 + 三份实验文档），
而第一次修复 `3608e24` **只清了 `references/`**——`rag/` 与实验文档继续传播
已被撤回的结论，**又过了 5 个提交**才由 `2dabb90` 清掉。

> **修复不完整本身就是一种腐烂**：它比原始错误更难发现，因为大部分文件已经对了。

**可机械检测吗**：**否**（单点采样这件事原理上无法机械判定）。但**传播面
可以**：任何"撤回某结论"的提交，判据必须包含**该原句在全仓 0 命中**
（`references/`、`rag/`、`docs/`、`src/`），而不只是"我改的这几个文件里没有了"。

**通用教训**：**推广前先问"这个结论是在几个采样点上测的"。**
凡标「实证 / 实跑 / live」却**没写采样点坐标或样本量**的结论，一律降级标注。
单点结论不得写成全局属性。

### I-6 门禁的宣称超过它实际做的

**现象**：新写的门禁**宣称覆盖的面大于它真正校验的面**。两例：

1. **委派缝门禁**宣称"全部纯转发壳…落盘即被覆盖"，却**从不校验关键字实参的值**。
   实测 28 条真实缝里 11 条是"位置 + 关键字混合转发"
   （`src/client.py::_build_form` 按关键字传 `ra`/`dec`），
   而 `ra=dec, dec=ra` 这种错位**不报 TypeError**，只是静默查错天区——
   旧判据对它返回**空清单**。
2. **零断言测试**：`for line in ...: if 命中: pytest.fail(...)`——**清单不存在时
   循环体一次都不执行，整条测试零断言恒绿**。讽刺的是它的职责正是"防门禁恒绿"。

**现在的护栏**：判据补上"两个关键字**互传对方的名字**"这一形态
（在机械上等价于键集上的 2-环，而纯改名是发散的、不可能产生 2-环，故无误报风险）；
零断言那条改成 `assert not offenders` + **额外断一次"确实读到了非空源码"**（防空读）。
同时 docstring 收窄成**两份清单**：守得住的 5 种退化 + 守不住的 3 种形态，
段首写明「**被扫到 ≠ 每种退化都被守住**」。

**可机械检测吗**：**部分**。门禁覆盖面本身有门禁
（`test/unit/meta/test_gate_scan_coverage.py` 断言门禁不得自带
`SCAN_DIRS = (...)` 清单，扫描面唯一真源是 `ops/audit/scan_roots.py`；
覆盖面靠**黑名单**而非白名单——白名单的缺口只能靠不断补，黑名单的排除项有限且稳定）。
但**"宣称得比做到的多"这一形态本身没有门禁**，靠的是写 docstring 时
把守得住与守不住的分开列。

**通用教训**：**门禁 docstring 是一份对外承诺，必须能被审计。**
"全部覆盖"这种话要么逐条列出覆盖形态，要么改成"被扫到 ≠ 全守住"。
判据宁可漏，**不要让一个爱漏报的门禁被集体关掉**。

### I-7 枚举不自洽：标题数词与表体/实测对不上

**现象**：两例。

1. `references/data-formats.md` 写「无值有**三种**编码」，**表体列了 4 行**
   ——这是**出生即自相矛盾**：写下的那一刻标题与表体就对不上，与外部事实
   是否被证伪无关。
2. 三份实验文档的术语表（`docs/eval-E1/E3/E4-*.md`）写「哨兵值**只有**
   -1000/-999」，实测还有 ≈-1000 的**带**（`-1004.07`/`-1004.08`…）、
   `uss_dr1` 的 `-32768`、字面 `nan`、空串 `""`——**共 5 种**。
   活了 **70 个提交**（全样本最长）。

**为什么是判分风险**：第 2 例被当**判分口径**传播到三份实验文档。
实测判分影响当时为零（E1 weighted 1.0 / E3 metascore 1.0，指纹逐字节相同），
但口径被写窄本身就是风险。

**现在的护栏**：哨兵口径一律指向 SSOT `evals/_data/null_sentinel.yaml`
（**判据与取值分离**：判定规则是 `value <= threshold`，不是 `==` 某一具体值），
三份实验文档只指向它、不再各自列举。

**可机械检测吗**：**部分**——`verify_counting_claims` 收的是
「`<文件>` … `<N> 行」这一种计数型断言；**"三种/两处/六个"这类中文数词
与表体条目数的一致性没有门禁**（中文数词不像阿拉伯数字那样能被 grep 核对，
最容易写飘）。这属**已知未设防**。

### I-8 断言站点方言拼写，而它是本仓映射的唯一依据

**现象**：`references/best-database-guide.md` 曾写
「注意站点把 greater 拼成 grater」。实跑（ps1 @180,30 300″，同锥逐项）：

| 操作符 | 行数 |
|---|---|
| `greaterequal` min15 | **1559** |
| `grater` min15 | **0**（回包 426 B，仅表头 CSV） |

**为什么贵**：那条旧文档是本仓 `greater→grater` 映射的**唯一依据**，
而这条映射实际是一条「把可读操作变成静默空结果」的路径——白名单外的操作符
站点**既不报错也不忽略**，而是收下后返回空表。**照着错误断言改本仓映射，
会造出一条静默返回空数据的通路。**

**现在的护栏**：映射已从 `build_query_form` 删除，`grater` 被排除出白名单，
白名单外显式 `ValueError`（fail-closed，铁律 5）；
`test/unit/protocol/test_operation_whitelist.py::test_greater_is_not_silently_rewritten_into_grater`
钉死它不得被改回去，且**断言那句反直觉的实测结论必须留在 docstring 里**，
否则下一个人会照旧文档改回来。

**可机械检测吗**：**否**（外部系统事实只能实跑）。但订正时有一条可复用的纪律：
**订正时同时标注仍未取证的部分**——「`grater` 在站点表单下拉里到底有没有这一项」
**当前未取证**（表单页三次尝试均未取到取值表），白名单的依据是**行数行为**
而非表单取值表。**纠错不要顺手制造一个新的绝对化断言。**

## J. 审计方法：检测员自己也会判错

这一节是元层面的：上面 I 类的 16 例里有相当一部分是**被检测报告找出来的**，
而检测报告本身的误报率与检出率**同量级**。不写这一条，下一个人会把
检测报告直接当修复清单用。

### J-1 检测员判错的比率与检出率同量级

**实测数据**（2026-10-05）：

- 检出：47 条注释断言逐条核实 → 14 条不符（**不符率 29.8%**）。
  即**每三条被检查的注释，约有一条与代码不符**。
- 误报：同一轮里 `37ec8fe` 推翻 D3 的 2 条判断；`2c47539` 推翻 D1 的 2 条
  （5 条里错 2 条，**误报率 40%**）。

**现在的护栏（做法层面，非门禁）**：修复者**逐条独立复核后再决定改哪一边**
——`fc550b4` 的分流结果是**16 条改注释、1 条改实现**；
`407b795` 的 7 处全是**改代码**，注释一字未动。允许推翻检测结论，
但**推翻必须附依据**，不是"我觉得"。

**可机械检测吗**：**否**。这是流程纪律。

**通用教训**：**把检测报告直接当修复清单用，会把 40% 的误报修成新的注释腐烂。**
若修复者不许推翻检测结论，清单就会变成不可质疑的圣经——**那是另一种 fail-open**。

### J-2 注释半衰期 ≈ 22 个提交，但这个数字由检测频率决定

**实测**（17 次检出事件的间隔，单位 = 提交数）：中位数 **22**、均值 34.6、
min 11、max 70；按日历时最长的一例活了 **7 天**。

**双峰结构**（这是最有指导意义的一条）：

| 峰 | 来源 | 间隔 | 解释 |
|---|---|---|---|
| 短寿峰 | 近期提交 | 11–21 | 审计轮次密集，检测紧跟 |
| 长寿峰 | 初始导入提交 | 62–70 | 导入后无审计，靠一次性批量检测才捞出来 |

> **推论：这个数字是被"检测频率"决定的，不是被"腐烂速度"决定的。**
> 真正的腐烂速度需要"无审计期"的对照样本，本仓只有初始导入之后那一个。

**通用教训**：**"最近没人报"不等于"没问题"，只等于"最近没查"。**
提高检测频率比提高注释质量更能压低半衰期。
