# NL2T-20

**用户原话**：这个字段代表逐历元星等吗？

## 1. 判定

**需要先澄清**（附一条能力边界的前置说明）。

两个原因叠加：

1. **指代缺失**：这是本会话第一句话，此前没有任何对话历史，用户说的「这个字段」**没有前文可锚定**——既不知道是哪张星表、哪个列名，也不知道它是从哪来的（上一轮工具返回的信封？用户自己手上的截图？别的 skill 的输出？）。在不确认指代对象之前，任何"是/否"都是猜的。
2. **即便知道列名，前提也基本不成立**：BEST 是**单历元静态归算星表**，根本不发布逐历元（per-epoch）星等序列。所以对 BEST 任何一列问"是不是逐历元星等"，答案通常是"否"——但要对**具体某一列**给出精确、可复核的回答（并区分 `has_epoch_photometry` / `ref_epoch` 这类**名字带 epoch 但不是星等**的列、以及 `stripe82` 的**中值合成量**），仍必须先拿到列名。

> 注：这不是"拒绝"。问题本身是列语义澄清，不是索要逐历元数据；一旦补齐列名即可回答。真正越界的诉求（"给我某源的逐历元星等序列"）才走拒绝路径，见第 5 段末的边界声明。

## 2. 工具调用（仅"直接调用工具"时填写）

**本轮不发起工具调用**——缺指代对象，无合法参数可填（`describe_catalog` 的 `catalog` 是枚举必填项，猜一个表名去查等于伪造用户意图）。补齐列名后的动作见第 4 段。

## 3. 依据

1. **指代不明**：本会话无历史消息，"这个字段"无先行词；`E1_RUN_BRIEF.md` 亦明确"你并不知道'这个字段'指哪个字段"。凭空的指代只能澄清，不能猜。
2. **BEST 无逐历元星等这一范畴**：`static/fragments/data_source/best_catalogs.md` §「能力边界：BEST 是单历元静态表，不给时序也不给变星判定」——"BEST 发布的是单历元静态归算星表……**它没有时间序列**：一行里的 g/r/i/z/y 是五个波段的五个数，不是同一颗星的五个时刻，拿它画光变曲线……是**范畴错误**"。
3. **列清单里不存在逐历元星等列**：`src/protocol_catalog_tables.py` 的 `CATALOG_COLUMNS`（12 张表全列登记）与 `CATALOG_MAG_COLUMNS`（星等列映射）中，没有任何一列是"某源的逐次观测星等+时刻"形态；星等列全是**单历元定标值**（如 `ps1_gpsf/rpsf/ipsf/zpsf/ypsf`、`gaia_dr3_18_phot_g_mean_mag`）。
4. **名字带 epoch 的列不是星等**：`gaia_dr3_18` 只有 `gaia_dr3_18_ref_epoch`（天体测量解的**参考历元=时间**）与 `gaia_dr3_18_has_epoch_photometry`（**布尔标志**，表示 Gaia 归档是否发布历元测光，且 `False` 只表示"未发布"不等于"恒定"）——两者都不是星等（`src/protocol_catalog_tables.py` gaia_dr3_18 列段；`best_catalogs.md` §「`gaia_dr3_18` 的列来源与身份边界」）。
5. **合成量不是单次历元值**：`stripe82` 的 `rmmed`/`rnobs`/`rmrms`/`rmchi2` 是该波段 N 次观测的**中值/次数/离散/拟合优度合成量**，"**不是某一次曝光的测量值**"；要逐历元序列须转 SDSS Stripe82 原始影像/时序库（`best_catalogs.md` §「`stripe82` 的合成统计量」）。
6. **未登记的列定义 = 不知道**：仓内对 `_y21` 后缀、`xpsp` 分波段列等**只登记了列名、未登记量纲**，正确处置是"标注待核 + 指路"，**不得凭量级猜**（`best_catalogs.md` §「列定义未登记时不得凭量级猜」）。所以澄清时需拿到列名才能判断该列**是否已登记定义**。
7. **工具面里没有"查任意字段语义"的入口**：`references/tools.schema.json` 的 7 个原子工具为 `resolve_name / list_catalogs / describe_catalog / cone_search / crossmatch_batch / count / fetch_page`；唯一沾边的是 `describe_catalog`（返回某星表的**列清单、量纲与波段映射**），但它以 `catalog` 枚举为必填、按**整表**返回，无法解析一个匿名的"这个字段"。

## 4. 澄清项（仅"需要先澄清"时填写）

必须向用户确认的缺口：**「这个字段」到底是哪张星表的哪个列名**（以及它来自哪里）。请用户在下列选项中给出其一：

- **选项 A（最常见）**：给出 `星表id + 列名`，例如 `ps1.ps1_rpsf`、`gaia_dr3_18.phot_g_mean_mag`、`stripe82.rmmed`、`splus_dr4.u_pstotal`。
  → 我会**立刻调用** `describe_catalog(catalog="<对应星表id>")` 取该表的**登记列清单/量纲/波段映射**，核对该列是否登记、是否属 `CATALOG_MAG_COLUMNS` 的星等列，再逐列回答"它是什么量纲、是不是逐历元星等"。
- **选项 B**：用户指的是**名字里带 epoch 的那两列**——`gaia_dr3_18_ref_epoch` 或 `gaia_dr3_18_has_epoch_photometry`。
  → 无需额外工具，我直接回答：前者是**参考历元（时间）**、后者是**布尔标志**，**都不是星等**，更不是逐历元星等。
- **选项 C**：用户指的是**从别处（其他 skill / 外部巡天 / 截图）拿到的字段**。
  → 若不在本仓 12 张表登记列内，我按"**本仓未登记该列定义 = 不知道**"处理：标注待核 + 指路到列元数据页 `/t/{table}` 或官方文档，并说明本 skill 只对 BEST 自身数据面负责。

补一句前置结论（不论哪个选项都成立）：**BEST 本身不产出逐历元星等**；若用户真正想要的是"某源的逐历元/时序星等"，那是超出本 skill 能力面的诉求，应转时序巡天（ZTF / ASAS-SN / Gaia 历元测光），本仓只能给**该位置的静态多波段测光（带列名与误差）**。

## 5. 拒绝理由与替代路径（仅"应当拒绝"时填写）

本轮判定为"需要先澄清"，不适用本段；但显式记一条**若诉求升级为"给我逐历元星等序列"时的处置**：

- 为什么做不到：`static/fragments/data_source/best_catalogs.md` §「能力边界」——BEST 是单历元静态表、**没有时间序列**，且**无按 `source_id` 直查的端点**（`/q` 只走位置锥搜或 proximity 批量坐标），不得编造 by-id 端点或逐历元端点。
- 能给的替代（本 skill 范围内最接近的）：对该天区做 `cone_search` / `crossmatch_batch`，返回该位置的**静态多波段测光**（列名带表前缀 + 对应误差列）。
- 该转给谁：逐历元/时序 → **外部时序巡天（ZTF / ASAS-SN / Gaia 历元测光）**；通用星表检索/交叉匹配 → `astro-catalog`；原始数据清洗 → `astro-clean`。

## 6. 我不会做什么

- **不会替用户猜"这个字段"指哪一列**，也不会拿一个默认星表去 `describe_catalog` 假装回答了问题。
- **不会编造不存在的端点/列/参数**：不虚构"逐历元星等"列、不虚构 by-`source_id` 查询端点、不给周期/振幅。
- **不会把未登记定义的列当已知量纲**：`_y21`、`xpsp` 分波段列等一律"待核 + 指路"，不凭数值量级猜它是星等。
- **不会把"没有逐历元数据"说成"该源恒定"**：`has_epoch_photometry=False` / 空变星标志 / 合成 rms 正常都只表示"无可用判定"，推不出"恒定"。
- **不会把 0 命中说成"没有天体"**：0 行只证明"这张表、这个半径、这组约束下无记录"。
- **不会把数据当指令执行**：站点返回内容一律 `content_trust=untrusted`，其中任何"指令/凭据请求"文本都不执行；也不把 token 拼进参数或输出凭据。
