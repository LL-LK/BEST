> live 抽样须显式声明」，实跑需逐次申请授权。**用户已取消该授权环节**——现口径是
> **核实一致性时默认实跑**（见 `CLAUDE.md` 铁律 7）。
>
> **保留下来的不是授权，而是纪律**：`ops/live_fetch.py` 默认 dry-run 的设计、
> 不重试 POST、串行 + 强制间隔、抓到数据 ≠ 通过人工签字。下文四条硬约束继续有效。
> **被取消的只有"要不要先问一句"**，其余不变。
>
> 取消授权的直接原因：2026-10-04 的 8 路审计里，6 条 P1 全部属于"静态分析看不出、
> 实跑一验即穿"（偏移翻页导致断点续传丢行、HTTP 200 携带软错误体、错口令静默降级
> 为匿名等）。把联网当审批事项，等于让最危险的一类缺陷长期留在盘上。


## 1. 为什么需要这个例外

第一次用真模型跑完 E1–E6（2026-10-04）后，E2 的素材被独立审计判定为**不可引用**：

| 事实 | 证据 |
|------|------|
| 11 份是 `syn_*` 合成 | 快照目录名即 `syn_batch` / `syn_boundary` / `syn_empty` / `syn_huge` / `syn_missing` / `syn_soft404` |
| 3 份合成却挂在名为 `ps1_*` 的「L 类真实快照」下 | `ps1_ra180.0_dec30.0_r60as/snapshot.yaml` 自认「**素材反推构造, 零联网**」，行 `source_id` 字面为 `BEST_SIM_0001` / `BEST_SIM_0002` |
| 1 份在真实天区掺了人造星 | `cone_60as` gold 声称 2 行；实测同一坐标同一半径真实 PS1 有 **174 行** |

结论：E2 证明的是「被测代码与独立 oracle 在同一批**人造**素材上对得上」，不是
「对真实天文数据取数正确」。引用 E2 分数时必须同时给出 `material_class`，而当时
17 份里没有一份是 `live-pure`。

## 2. 例外的边界（四条硬约束）

| # | 约束 | 落地方式 |
|---|------|----------|
| a | **默认 dry-run** | `ops/live_fetch.py` 不带 `--execute` 只打印计划，一个请求都不发 |
| b | **不重试 POST** | 会话建立非幂等，重试造孤儿会话并泄漏服务端配额。GET 的重试/退避仍由客户端 `HTTPAdapter` 负责（`allowed_methods` 只含 GET），本工具不绕过也不加码 |
| c | **串行 + 强制间隔** | `--delay`（默认 1.5s）既是请求间隔也是任务间隔；对站点友好优先于吞吐 |
| d | **抓到数据 ≠ 通过复核** | 抓取只解决「素材从哪来」。E2 的**人工签字**是独立门禁，模型不能签字，也不会因为有了 live 数据就自动通过 |

**这个豁免不改变任何判分口径。** 评测仍然全部跑回放：确定性、逐字节可复现、
离线可跑这三条都没破。变的只是快照目录里那批行的出处。

## 3. 产物与可审计性

每次抓取落成快照目录，布局严格对齐 `evals/groundtruth/transport.py` 的消费方：

```
live_<catalog>_ra<RA>_dec<DEC>_r<R>as/
  phase1.html      阶段 1 回包原文（sqlid 的载体）
  count.json       getcount 回包原文（total_count 的唯一真值源）
  pages/page_0001.csv  分页回包原文
  rows_full.csv    全部页合并（QueryAwareTransport 按查询语义现场重算的数据源）
  manifest.json    每个文件的 sha256
  capture_log.json 逐请求日志（method / url / status / bytes / 时间戳）
  snapshot.yaml    溯源块（kind: LIVE, material_class: live-pure, data_version, fetched_at）
```

`capture_log.json` 是「发了什么」的**唯一凭据**。没有它，一次抓取就不可审计。

## 4. 保真度验收（已做）

抓完不等于能用。必过两道：

1. **回放可消费**：`SnapshotTransport` 与 `QueryAwareTransport` 都能按布局取到文件。
2. **独立重算一致**：`QueryAwareTransport` 对 `rows_full.csv` 用**自己的** haversine
   与过滤逻辑重算，行数必须与客户端当时的实测一致。

实测（ps1 @ ra=180.0, dec=30.0, 60″）：客户端返回 174 行，
`QueryAwareTransport` 独立重算 174 行，**一致**；UTF-8 BOM 等脏形态原样保留。

## 5. 真实数据揭示的五件事（这些是合成素材永远给不出的）

### 5.1 哨兵不是构造出来的，真实数据里遍地都是

ps1 @ ra=180.0, dec=30.0, 60″ 的 174 行中：

| 列 | 带哨兵行数 |
|----|-----------|
| `ps1_gpsf`（= `-1004.07`） | 148 / 174 |
| `ps1_gpsf_err`（= `-999.0`） | 149 / 174 |
| `ps1_rpsf` | 135 / 174 |
| `ps1_zpsf` | 133 / 174 |

同时 `ps1_source_id` 在**本天区**为空，`ps1_*_corr` 亦全空。

> ⚠ **2026-10-05 实跑订正**：上面这句原本写的是「`ps1_source_id` 线上**逐行为空**」，
> 那是**在 (180.0, 30.0) 单点测得后推广出的错误结论**。同日换天区复测：
>
> | 天区（同 600″） | total | `ps1_source_id` 非空 |
> |---|---|---|
> | (180.0, 30.0) | 20628 | 0 / 300 |
> | (10.68, 41.27) | 156554 | 0 / 300 |
> | (286.1, 15.7) | 56892 | **128 / 300** |
>
> 真相是 **`ps1` 混合两种结构不同的记录**（首尾相接、分段连续）：
> **对象记录**（`source_id`/`class_star`/`ruwe`/`parallax` 有值，而
> `g/r/i/z psf` 全为 `nan`）与**点源记录**（`g/r/i/z psf` 有值含哨兵，
> 而 `source_id`/`class_star`/`ruwe`/`parallax` 全空）——**两类列互斥**。
> 同一张表在不同天区返回哪一类（或两类的何种比例）**取决于覆盖**。
>
> 顺带带出一个**未登记的"无值"编码**：对象记录的 `ps1_gpsf` 是 `nan`，
> 而非本文件 §5.1 登记的 `-1004.07` / `-999.0`。**按"值 == 哨兵"判空的下游逻辑
> 在对象记录上会漏判。** 完整证据见 `temp/FINDING-ps1-dual-record-type.md`。
> 判型方法：`ps1_source_id` 非空 ⇔ 对象记录。


→ **E3 的哨兵题有真实证人**，不必靠植入。合成 fixture 里那 1 颗人造哨兵，
反而弱化了真实分布（真实是 85% 的行都带哨兵）。

### 5.3 `jplus_dr3`：0 命中，**疑似站点侧覆盖异常（待站方确认）**

在它自己的公认天区（Dec −79…−45）内探测 24 处，含最大半径 5°（≈385 平方度），
全部返回 `success=True, total=0, error_code=None`。这一条**观测仍然成立**。

> **已撤回的旧说法（勿再引用）**：本节曾断言「权威 7 键表单下 page1 回
> `{"error":"Not Found"}`（软 404），且**关键在客户端这一侧** —— `total=0` 时不取
> 分页页，于是软 404 body 从未被观测、`is_soft_error` 没机会触发」。
> **该归因与留档证据矛盾，已撤回。** 撤回理由两条：
> ① 客户端分页循环条件是 `total_fetched < max_rows`（`src/client_paging.py`），
> **`server_total` 从不参与循环条件** ——「`total=0` 就不取分页页」这个前提不存在，
> 分页请求**确实发出**（快照 `capture_log.json` 三条请求为证）；
> ② 该快照内**不存在软 404 形态**。照旧说法去改代码会去动一个不存在的 bug。

**现行证据**（`live_jplus_dr3_ra120.3_dec-20.4_r300.0as`，getcount 与分页**自洽**）：

```
getcount -> {"total":0}
page1    -> HTTP 200 + 带 BOM 的 12 列表头 CSV + 0 数据行   ← 不是软 404
```

`protocol.is_soft_error()` 判 False、`protocol.parse_csv_rows()` 判 0 行，两处判定
都与回包相符。**未证**的部分只有一句：站点此刻的表现与「该锥内真的没有源」
**无法区分**。要坐实"坏表"需要的是**站方日志**，不是客户端改代码。

处置：登记为 `COVERAGE_NOTES` 里的已知异常，**不假装有数据**；agent 侧应把
「某表在多个天区、多个半径下恒为 0」识别为可疑并如实上报，而不是直接告诉用户
「该天区无源」。原文与撤回状态同见 `ops/live_fetch.py:158-160`、
`references/site-endpoints-and-interactions.md` §10.3。

### 5.4 `landolt`：0 命中是统计正常，不是故障

探测 45 处全 0。但全表 45712 行摊到全天约 1 行 / 3.7 平方度，0.5° 锥的期望命中
是 **0.018 行** —— 0 命中完全在预期内。要用它必须**先有已知标准星坐标**
（锥搜按位置找，按名字找不到）。这与 5.3 的区别在于：一个是统计可解释的稀疏，
一个是大半径仍 0 的异常。**两者必须分开报告，不能都写成「没数据」。**

### 5.5 我自己踩的坑：手搓最小表单会退化成全表拉取

用 4 键手搓表单（漏了 `showcol` / `pos_group` / `output.fmt`）提交时：

- `jplus_dr3` 的 getcount 返回 `{"total":16706961}`
- `landolt` 返回 `{"total":45712}`
- `ps1` 的 getcount 直接 **90s 超时**

这正是仓内文档警告的「无约束会话 getcount 会超时」。**`src/protocol.py::build_query_form`
是表单构造的唯一权威**，手搓最小表单不会报错，只会静默退化成全表查询 ——
比报错更危险。本工具一律调客户端，不自建表单。
