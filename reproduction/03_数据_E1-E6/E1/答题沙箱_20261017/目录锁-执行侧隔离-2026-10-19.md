# 目录锁 · 执行侧隔离（2026-10-19）

> 目的：把「被测模型不该看」的文件从**纸面规则**变成**物理拒绝**。
> 隔离主体：`廖CG\CodexSandboxUsers`（成员 `CodexSandboxOffline` / `CodexSandboxOnline`，即模型侧进程）
> 放行主体：`廖CG\user`（执行会话）—— 加锁后执行侧一切照旧。

---

## 一、为什么原来"不能看"只是纸面

`sbN/SANDBOX-RULES.md` 写着「不可以看：`_exec/`、`_lock/`」，`ALLOWED-FILES.md` 也声明
「不在白名单里的东西物理上不存在」。但上锁前的实测 ACL 是：

| 目录 | 上锁前 ACL |
|------|-----------|
| `sb1/_exec` | `Allow CodexSandboxUsers ReadAndExecute`（继承） |
| `sb1/_lock` | `Allow CodexSandboxUsers ReadAndExecute`（继承） |
| `sb1/answers` | `Allow CodexSandboxUsers ReadAndExecute`（继承） |
| `sb1/skill` | `Deny Everyone (WD,AD,DE,DC)` + `Allow CodexSandboxUsers ReadAndExecute` |

也就是说：`skill/` 上那条 deny 只挡**写/删**，`_exec/`、`_lock/` **一条 deny 都没有**。
模型侧的组能直接读全量题册。规则说得再硬，ACL 是开的。

## 二、哪些文件不能给模型看

按泄露危害排序：

| 等级 | 对象 | 为什么 |

## 三、已实施的锁

对 `廖CG\CodexSandboxUsers` 加 **显式 Deny `Read`**（`ReadData`+`ListDirectory`+`ReadAttributes`
+`ReadExtendedAttributes`+`ReadPermissions`），目录用 `(OI)(CI)` 继承到所有子文件：

| 对象 | 类型 |
|------|------|
| `sb1\|sb2\|sb3/_exec/` | 目录（整棵） |
| `sb1\|sb2\|sb3/题卷/per_task/` | 目录（整棵） |
| `sb1\|sb2\|sb3/题卷/context/` | 目录（整棵） |
| `sb1\|sb2\|sb3/_lock/净化日志.txt` | 单文件 |
| `_builder/`、`_验收/` | 目录（整棵） |
| 根目录 8 个 `.md`（含本文件） | 单文件 |

共 **11 个目录 + 12 个文件 = 23 个显式锁点**（全树统计，不含继承项）。

验证（`Get-Acl` 抽查，显式项 inherit 到子文件）：

```
sb1\_exec                          DENY (explicit) Read
sb1\_exec\TASKS.md                 DENY (inherited) Read
sb1\_exec\题包\NL2T-01.md           DENY (inherited) Read
sb1\题卷\per_task\NL2T-01.txt       DENY (inherited) Read
sb1\_lock\净化日志.txt               DENY (explicit) Read
_builder\build_sandboxes.py        DENY (inherited) Read
判分报告-sb1-r3-2026-10-19.md       DENY (explicit) Read
```

执行侧（`user`）复测：`_exec/TASKS.md`、`_lock/净化日志.txt`、`_builder/build_sandboxes.py`
全部**仍可正常读取** —— deny 只落在模型组的 SID 上。

锁后复检：三箱 `sandbox_lock.py verify` 全 **PASS**（文件 199 / 文本扫描 192，命中 0 条），
`compare_boxes.py` 判红 0 条。ACL 不影响哈希校验与台账比对。

## 四、边界（别把它当万能锁）

1. **挡得住**：模型侧进程（`CodexSandboxOffline/Online`）读取、列目录、误挂载；
   以及任何"顺手 grep 一下"的行为 —— 这些路径现在直接返回 Access Denied。
2. **挡不住**：以 `user` 或管理员身份运行的程序。ACL 的 owner 仍是 `user`/Administrators，
   `WRITE_DAC` 没收回，**同账户主动改 ACL 就能解锁**。这不是缺陷，是设计：
   执行会话必须保留解锁能力，否则重建沙箱时会把自己锁死。
3. **真正的硬防线仍然是"物理不含"**：`answers/` 里没有答案、`skill/` 里没有标注、
   `题卷/` 里没有判分口径。ACL 只是把"可以读但被告知别读"变成"读不到"。
4. **重建沙箱会重置 ACL**。`build_sandboxes.py --apply` 会重写三箱，
   `seal --acl` 只加 `skill/`、`题卷/` 的写拒绝 —— 本次的读拒绝**不会自动恢复**，
   重建后必须重跑本文第三节的清单。

## 五、解锁（重建或临时放开时）

```powershell
$root = "<USER_HOME>\E1-答题沙箱-2026-10-17"
$grp  = New-Object System.Security.Principal.NTAccount("CodexSandboxUsers")
Get-ChildItem -LiteralPath $root -Recurse -Force |
  Where-Object { $_.PSIsContainer -or $_.Extension -in ".md",".txt" } |
  ForEach-Object {
    $acl = Get-Acl -LiteralPath $_.FullName
    $hit = $acl.Access | Where-Object {
      $_.AccessControlType -eq "Deny" -and -not $_.IsInherited -and
      $_.IdentityReference -like "*CodexSandboxUsers*" }
    if ($hit) { foreach ($r in $hit) { $acl.RemoveAccessRule($r) | Out-Null } ; Set-Acl -LiteralPath $_.FullName -AclObject $acl }
  }
```

> 只移除**显式** deny，继承来的会随父目录消失自动消失。
