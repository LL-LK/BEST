## 二、四处问题，逐条改法

### 2.1 排序列写法被判死（NL2T-21）

**问题**：`tools.schema.json` 对 `sort` 的原文是「服务端排序列，**如 `ps1.rpsf` 或裸名 `rpsf`**」。
sb1/sb3 写的 `ps1.rpsf` 正是 schema 给的示例，gold 写 `ps1_rpsf`，param 维走 `grade_exact`
字符串相等 → 判 0；sb2 写裸名 `ps1_rpsf` 反而满分。**同一份 schema 的三种合法写法，只有一种能过。**

**改法**（`graders.py`）：新增 `_sort_core()` + `_same_sort_column()` + `sortcol` 归一化器，
把 `.`/`-`/空白归一成 `_`，然后判"相等 **或** 互为 `_` 分隔的后缀"。

**为什么不是放水**（`fix_controls.py` ①）：

| 输入 | 结果 |
|------|------|
| `sort="ps1.rpsf"` / `"rpsf"` / `"ps1_rpsf"` | 1.0（三种合法写法） |
| `sort="ps1.gpsf"`（波段错） | **0.0** —— 与 gold 互不为后缀 |
| `sort="ps1_rpsf_err"`（错列） | **0.0** |
| 漏传 `sort`（schema 无默认值） | **0.0** |

### 2.2 标注比题面严：半径与成员表都是"猜出题人"（NL2T-09）

**问题**：题面 `按名字查 Betelgeuse 在 BEST 的标准星记录。` 既没给半径、也没点名哪张表；
gold 却写死 `radius_arcsec: 3.0` + `catalog: scr_galah` + `nearest_only: true`。

两条旁证说明这不是能力问题：
- 3″ 在整份可见面里只出现过一次 —— `static/fragments/target_type/best_ttype.md` 的
  "`ps1`=3.0 arcsec"，那是**目标匹配**口径，与标准星无关；
- `nearest_only: true` 恰好等于 `crossmatch_batch` 的缺省值（题包第 110–111 行），
  而 `cone_search` 的缺省是 **false** —— 这条 gold 很像从 crossmatch 的默认值搬过来的。

**改法**（`tasks.yaml` + `graders.py`）：
- `cone_search` 删掉 `radius_arcsec` 与 `nearest_only`（题面没给的一律不进判据）；
- `catalog` 改成 `[scr_galah, scr_lamost, xpsp]`，判分器新增**列表金标 any-of**；
- convert 维：一条期望调用里**所有**换算键都是占位符时不计入分母（09 本就没有换算可判，
  旧实现要么记 0、要么白送 1.0）。

**考点还剩什么**：`std` 是组不是表（传 `std` → param 判错）、名字必须经 `resolve_name`
解算后落标准星成员表（传 `ps1` → 判错）。**代价**：不再区分"挑中哪一张成员表" ——
想恢复这个考点，只能在题面里写明 `scr_galah` 再重建沙箱（那会让本批归档答案对该题失效，
见 §5）。

### 2.3 06 与 12 的 `count` 口径互斥

**问题**：两题都是"看看有多少"，06 的 gold 要求锥搜后再 `count(sqlid)`，12 却把 `count`
记成多余调用 → sb1/sb2 在 06 满分、12 扣到 0.812，sb3 反过来。**行为一致的模型不可能两题都满分。**

**改法**：
- 标注：06 的 `count` → `optional: true`（另加 `preferred: true`，只让金标准示范轨迹保留它，
  不参与打分）；12 补一条 `optional: true` 的 `count`。两题从此口径一致：**调可以，不调也可以**。
- 判分器：toolset 精度分母不再计入 `optional` 工具。这是补文档欠账 —— 注释一直写
  "optional 两边都不计"，但旧实现只把零请求探查摘出去，非零请求的 optional 一出现就把
  precision 打到 0.5。
- **clarify 路由例外**：那里的 `optional` 是 `required|optional|零请求` 的合并白名单，
  若也豁免，"澄清前就开查"在 toolset 维就再也记不上（这条是我改第一版时踩到并修掉的）。

**为什么不是放水**：06/12 的半径判据照旧 —— 12 传 `0.5`、06 传 `5` 仍判死（controls ②）。

### 2.4 `partial_credit` 从未落地（NL2T-11）

**问题**：标注写着"显式声明口径判 0.5"，`graders.py` 全文没有这个词。三箱都选择
"说明 std 是分组 + 逐张查三张成员表"，一律判 0。

**改法**（`graders.py`）：clarify 维新增 **Assumption-Declared** 通道，三个门同时开才生效：
1. 该题标注里有 `partial_credit`（目前只有 11，不会全局放水）；
2. 回答**没有在拦着用户问**（认 `请指明/请确认/请补充/哪一张…` 这类祈使标记；
   **刻意不认裸问号** —— "要不要我再放宽半径？"这种收尾提议也带问号，实测 sb3 就因此被判成"在问"）；
3. 有声明措辞（`我按/假定/口径取…` 或 `不是表/成员表/分组/逐张…`）**且**点名 ≥2 个具体候选表。

**为什么不是放水**（controls ④⑥）：
- 只说"已查询 0 行" → **0.0**（未声明）；
- 真的问了、首轮零调用 → **1.0**；
- **问了又查** → **0.0**（声明式假设不能洗白硬执行）；
- 17/19 等无 `partial_credit` 的题 → 该通道**不启用**。

> 11 的最终分是 **0.3**（toolset 0 + clarify 0.5 + redundant 1.0）：partial_credit 只抬 clarify，
> `route: clarify` 首轮硬查在 toolset 维照扣。这是刻意的 —— 次优解给一半，不等于没代价。

## 五、留给你的两个口径选择

1. **09 不再考"挑哪张成员表"**。如果你的设计意图是"必须挑对一张并声明口径"，那得改题面
   （写明 `scr_galah`）—— 但改题面就要重建沙箱，且 2026-10-18 这批归档答案在 09 上会失效
   （它们答的是 60″ 三表）。当前选择是"按题面能推出来的最大公约数"。
2. **06/12 的 `count` 现在是双向可选**。如果你认为"先 count 再决定"是必须养成的习惯，
   那应该把 06 的 count 改回必需、同时把 12 也改必需（而不是一必需一多余）。
