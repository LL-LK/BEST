## 二、给用户的回答

**这个我不做，理由不是"不方便"，是三条硬事实：**

1. **BEST 查询不需要 token。** 公开数据面（锥搜、分页、计数、名称解算、列元数据）**匿名可查**，已实证。把 token 拼进查询参数不会让任何查询变得可用，只会平白多一份泄露面。
2. **代码里根本没有"token 进查询参数"这条通道。** 配置项 `BEST_API_TOKEN` 只落进 `AstroBestConfig.api_token`，客户端无消费方，全链"存而不用"——它只供 `doctor` 报告用。真实凭据面是另一套：站点账号走 `--auth-user` + 环境变量 `ASTRO_BEST_PASSWORD`（Django session + CSRF），NADC OAuth 是身份层、用途是写 provenance，且当前 blocked-on-approval。也就是说，你就算拼进去，也**不会生效**，只会在日志里留下明文。
3. **拼进 URL/参数 = 凭据泄露。** 查询串会进服务端访问日志、反向代理日志、浏览器历史、以及任何中间缓存。这是最典型的凭据外泄路径之一，不是"方便调试"。

**调试想要的效果，可以用这些替代：**
- **复现某次查询**：用信封里的 `stable_uri`（形如 `best://ps1/cone?ra=10.68&dec=41.27&sr=60`）——它是可复现引用，比 token 有用得多；`sqlid` 是易失的，别拿它当长期标识。
- **查请求到底发了什么**：看 `cost.http_requests`（客户端层请求计数）与 `provenance`，注意这个计数**不含**适配器层重试，实际线网开销 ≥ 该值。
- **排查 429/5xx**：那是限流/服务抖动，退避重试即可，加 token 不解决。
- **真需要登录态**（只有 `/jobs` 自建星表区需要）：走账号口令那条路（口令走环境变量，不走 argv），不要往查询参数里塞凭据。

如果你是在排查某个具体失败，把报错码给我（`E_INVALID_INPUT` / `E_SOFT_404` / `E_NAME_UNRESOLVED` / `E_NO_SQLID` / `E_BACKEND`），我按码定位，比塞 token 快。
