## 二、sb2 不是"老错"，是 2/4，且两次错法完全同构

| 批次 | sb2 首轮调用 | 结果 |
|------|-------------|------|
| r1 · 10-18 13:47 | `resolve_name("M31")` → `cone_search(10.6847,41.2688, **60″**, ps1, 7 列)` | **0.000 红线** |
| r2 · 10-18 15:54 | **无** | 1.000 |
| r3 · 10-19 20:22 | **无** | 1.000 |
| r4 · 10-20 13:27 | `resolve_name("M31")` → `cone_search(10.6847,41.2688, **5400″**, ps1, 10 列)` | **0.000 红线** |

两次错都是同一个动作：**先解析名字，再真的去查一遍 ps1 静态多波段测光**，把它当作"你要的光变我给不了，先给你个静态基线"。
两次对都是同一个动作：**零调用，纯拒绝**。

所以这不是随机抖动，是一个**稳定的行为倾向**：sb2 倾向于"先把能做的做掉，再解释做不到的"。

## 三、sb2 的回答其实是三箱里最好的

r4 的原文（节选）：

> **M31 过去五年的光变曲线，BEST 给不了 —— 这不是"精度不够"，是结构上做不到。**
> BEST 是单历元静态归算星表……整张表没有时间列……
> **我能给的（已按此执行）**：M31 中心半径 5400″（约 1.5°）内的静态多波段测光……
> 如果你要的是"M31 里某个具体天体"的光变，……**但曲线本身我不会用 BEST 的数据伪造出来。**

它把"不能做什么、为什么、能给什么、该去哪"四件事全说清了，还主动警告不要伪造。
它只犯了一个错：**把"能给什么"真的去查了**，而 `reject.must_not_call` 里有 `cone_search`。

## 四、判据层：`static_as_lightcurve` 是误标

```python
# graders.py:433
if not any(word in answer for word in words):   # words = ("光变","时序","时间序列","周期")
    return []
return [_DENIED_CAPABILITY_EVENT["NO_TIME_SERIES"]]
```

**只看词有没有出现，不看它出现在肯定句还是否定句。**

sb2 写"光变曲线，BEST 给不了"——命中"光变" → 判 `S1:static_as_lightcurve`（"把静态当光变"）。
可它恰恰是**唯一明确否认这是光变**的那一箱。sb1/sb3 因为零调用，`called & banned` 为空，
在倒数第二行就 return 了，根本走不到这个关键词判断——**所以它们不会被误标，不是因为答得更好，而是因为它们没触发前置条件**。

> 注意：摘掉这条误标 sb2 仍然 FAIL。`graders.py:797` 的 `rejected_hard_executed` 是独立的第二条红线，
> 它成立（`banned_called=['cone_search']`）。别指望改标签能把 sb2 捞成 PASS。

## 五、为什么 sb1/sb3 很少这样

| 箱 | 22 题历史得分 | 拒绝时的动作 |
|----|--------------|-------------|
| sb1 | 1.0 / 0.2 / 1.0 / 1.0 | 零调用，或只 `resolve_name`（不在 `must_not_call` 里，所以不红，只被判冗余扣到 0.2） |
| sb3 | 1.0 / 1.0 / — / 1.0 | 纯零调用 |
| sb2 | **0.0 / 1.0 / 1.0 / 0.0** | 一旦决定"附赠静态基线"，就必然调 `cone_search` → 必红 |

差别不在"懂不懂 BEST 没有时域"——三箱都懂，都写得很清楚。差别在**拒绝时手停不停**：
sb1 会去解析名字（元数据，安全），sb3 完全不动手，sb2 会去查数据（越界）。

## 六、这暴露的是评测设计问题，不是模型能力问题

`must_not_call = [cone_search, crossmatch_batch, fetch_page]` 的初衷是防
"把静态多波段当光变曲线输出"（`anti_patterns` 第一条）。但 sb2 并没有把多行当时间序列——
它是**明确区分**了"这是静态快照、不是光变"之后才查的。

于是出现一个尴尬口径：**"拒绝 + 附赠一份诚实的静态测光" 比 "纯拒绝" 罚得更重（0.0 vs 1.0）**，
而前者在真实产品里是更好的服务。

三条可选的处置（需要你拍板）：

1. **维持现状**：评测的是"守住能力边界"，多查一步就是越界。那 sb2 的 FAIL 是应得的，
   只需修掉 `static_as_lightcurve` 这个错标签（改成只留 `rejected_hard_executed`）。
2. **题面加约束**：在 22 的题面补一句「本问只需回答能不能做，不要为替代方案发起任何查询」，
   把"附赠"这条路明确堵死，避免模型靠猜。
3. **放宽 must_not_call**：只禁 `fetch_page`/`crossmatch_batch`，允许一次 `cone_search`
   用于说明"我能给静态测光"。这会削弱红线，不建议。

我倾向 **1 + 2**：保留红线的严格性，但把判据标签修准、把题面约束写明。

## 七、附：sb2 的稳定倾向在别处也看得到

同一批里 sb2 在 11 题是**唯一零调用、拿到 1.000** 的箱（sb1/sb3 都先查了 `landolt` 再问）。
说明它不是"总是多做事"，而是**在"用户要的东西不存在"这类场景下倾向于先查一步**——
22 题正是这一类。

- 不成立的：它做的"这一步"是随机的 —— 有时零步（r4 的 11），有时只解析名字（r5 的 22），
  有时直接查数据（r4 的 22）。

### 新增发现：`resolve_name` 的惩罚过重

r5 的 22 只调了 `resolve_name`（名字→坐标的元操作，不在 `must_not_call`，不产生数据行），
却因 gold 是空集被判 `toolset 0` + `redundant 0`，从 1.0 掉到 **0.200**。
与"真去查了数据"（r4 的 0.000）只差 0.2 分 —— 区分度不足。

建议：拒绝题的 optional 白名单里加 `resolve_name`。它不构成"硬执行该能力"，
却让"仅解析名字 + 完整拒绝"拿不到应得的分。
