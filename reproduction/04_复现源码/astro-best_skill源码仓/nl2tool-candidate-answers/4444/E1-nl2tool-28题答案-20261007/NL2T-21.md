# NL2T-21
## 用户原话
> RA=180.0、Dec=30.0、半径 60″ 内，这个天区最亮的源是哪颗？按 r 波段排。
## 判定
直接调用 —— 坐标/半径/波段三要素齐备，星表未指定则走工具缺省 ps1；用 `cone_search` 的服务端排序 `sort=<r 波段星等列>` + `order=asc` 一次取到最亮源，无需澄清，也无需先发零请求的描述类工具（列名已在协议层确定）。
## 期望调用
```python
from src.ai_tools import ToolBox

tb = ToolBox()
result = tb.cone_search(
    ra=180.0,
    dec=30.0,
    radius_arcsec=60.0,        # 用户口径 60″ 就是角秒，直接传，不换算成度
    catalog="ps1",             # 用户未指定星表 → 工具/schema 缺省 ps1
    sort="ps1_rpsf",           # r 波段 PSF 星等列（响应列名）；裸名 rpsf / 限定 ps1.rpsf 等价
    order="asc",               # 星等越小越亮 → 升序 = 由亮到暗
    nearest_only=False,        # "最亮" ≠ "最近邻"，必须关（这也是缺省）
    max_rows=1000,             # 工具缺省；服务端排序后首行即最亮
)

brightest = result.data["rows"][0]   # 服务端已按 r 星等升序 → 首行即 r 波段最亮的源
```
## 参数与换算
- `ra=180.0`：用户给 180.0，单位度（ICRS），原样传；合法域 `[0, 360)`。
- `dec=30.0`：单位度，原样传；合法域 `[-90, 90]`。
- `radius_arcsec=60.0`：用户口径「60″」本身就是角秒，直接传 60.0。**不做换算**——工具的半径参数单位是角秒（`units_note`：「radius in arcsec」），若误按度换算成 60/3600 = 0.016667 传进去，锥半径会缩到 0.0167″（几乎必然 0 行）；60″ 也远小于上限 18000″（=5°，`validate_search_radius`）。
- `catalog="ps1"`：用户未点名星表；`src/ai_tools.py` 的 `cone_search` 与 `references/tools.schema.json` 的 `catalog` 缺省值都是 `"ps1"`（Pan-STARRS All-Sky，全天覆盖且发布 r 波段）。这是取缺省，不是编造。
- `sort="ps1_rpsf"`：r 波段列名。`CATALOG_MAG_COLUMNS["ps1"] = {"gpsf":"g","rpsf":"r","ipsf":"i","zpsf":"z","ypsf":"y"}`，r 波段列剥前缀为 `rpsf`，响应列名 `ps1_rpsf`。协议层 `qualify_column` 接受三种拼写：裸名 `rpsf`、带前缀 `ps1_rpsf`、限定 `ps1.rpsf`。
- `order="asc"`：星等是「越小越亮」的逆向标度 → 升序（由小到大）即由亮到暗，首行就是最亮；用 `desc` 会拿到最暗的一颗。
- `nearest_only=False`：保持缺省并显式写出，表明「最亮」与「最近邻」不是一回事（详见陷阱 1）。
- `max_rows=1000`：工具缺省行数预算。排序生效时首行即答案，与锥内总源数无关；若 `total_count > 1000` 会置 `truncated=True`，但首行仍是最亮，不影响本问。

## 陷阱与错法
1. **把「最亮」当「最近邻」**：`nearest_only=True`（→ `cone_nearestonly`）只按到锥心的角距保留最近的一颗，返回的是「离 (180,30) 最近」的源，不是 r 最亮的。更阴的是它恰好也只回 1 行，表面像「答案」。
2. **order 方向搞反**：星等越小越亮，最亮要 `order="asc"`；用 `desc` 会得到锥内最暗的一颗。
3. **r 波段列名猜错**：传 `sort="r"` / `"rmag"` / `"r_psf"` / `"ps1_r"` 都不是 ps1 发布的列；`qualify_column` 是 fail-closed，会抛 `ValueError` → `E_INVALID_INPUT`（不会静默给错序）。正确写法只有 `rpsf` / `ps1_rpsf` / `ps1.rpsf`。
4. **单位弄错**：把 60″ 当度、当角分传，或把 60 换算成 0.016667（度）塞进 `radius_arcsec` —— 该参数单位恒为角秒。
5. **误用 `band`**：工具面 `cone_search` **没有** `band` 参数（`band` 只存在于 client 层 `src/client_query.py:375` 的 `cone_search`）。在工具面传 `band="r"` 会报 unexpected keyword；「按 r 波段」在工具面只能靠 `sort` 指到 r 列。
6. **拉全量再本地排序**：徒增行数与请求；服务端有 `sort`/`order` 就该用它。
7. **仓内证据缺口（如实标注，不改调用）**：对 ps1，分页默认注入的排序列 `ps1_source_id` 实测整列为空（`src/protocol.py:147-158` 的 H3-03 订正：ps1 是该表唯一「排序列为空」的星表），故 ps1 上「排序真生效」在仓内是「尽力而为、非契约」。因此若回包首行明显不像最亮（如 r 列有值但行序像随机），应把它标为可疑而非硬答；需要本地复核时对已取 `rows` 按 `ps1_rpsf` 再排一次，并在结论里注明这一来源限制。星等为空的行在 asc 下排在末尾（`uss_dr1` 实测 NULL 块在 desc 被顶到开头，即 NULL 视为最大），故首行仍是真值。
## 若需澄清，问什么
无需澄清。坐标、半径、波段三要素齐备，星表有明示缺省（ps1）。仅当用户本意是别的星表（`splus_dr4`/`uss_dr1`/`stripe82` 等也发布 r 波段，列名各不相同）时才需要追问星表——但那属于用户未提的可选偏好，不构成阻塞。
