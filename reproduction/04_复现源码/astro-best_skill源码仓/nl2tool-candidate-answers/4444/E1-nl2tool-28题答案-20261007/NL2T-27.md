## 参数与换算
- **无调用，故无参数可填。** 本 skill 的唯一对外工具面是 `src/ai_tools.py::ToolBox` 的 7 个原子工具（`TOOL_NAMES`，ai_tools.py:792-800）：`resolve_name` / `list_catalogs` / `describe_catalog` / `cone_search` / `crossmatch_batch` / `count` / `fetch_page`。七个全部是「名称解算 / 星表清单 / 列元数据 / 天区检索 / 坐标批量匹配 / 计数 / 分页取行」——**没有一个返回图像**，没有一个接受「出图/看图」类参数。`references/tools.schema.json` 的 `tools` 数组逐项核对，同样只有这 7 项，无 `image`/`cutout`/`preview`/`hips` 之类条目。
- **"这个天区"本身也缺参（第二重缺陷，但不是本题主因）**：原话用指示代词指代一个未出现过的天区，没有 ra/dec/半径，也没有可解析的天体名，任何检索类调用都无从填参。即便退一步把诉求降级为「取该天区的星表数据」，也仍需先解析出中心坐标。
- **降级路径（仅供说明，不是本题答案）**：若用户改口只要该天区的**源表数据**，才轮到 `cone_search`，其口径为：
  - `ra` / `dec`：单位**度**（ICRS），来自用户给定坐标或 `resolve_name(name)` 解算；
  - `radius_arcsec`：单位**角秒**，缺省 180″（=3′），上限 **18000″ = 5°**（`tools.schema.json` 的 `maximum`，由 `BestClient` 入口 `validate_search_radius` 强制）；
  - 换算口径：站点表单 `pos.radius` 是**角秒**，传度会得 0 行或 360 倍半径；`BestQuery.cone(radius_deg=度)` 与 `BestClient.cone_search(radius_arcsec=角秒)` 形参名/单位不同（data-formats.md §4）。1° = 3600″，故 5° = 18000″ 即上限。
  - 但这条只能拿到 CSV/JSON/VOTable 之类的**行数据**，仍然不是「能直接打开看的图」。

## 陷阱与错法
1. **幻觉出影像端点/工具**（最致命）：凭空编一个 `cutout`/`hips`/`image_preview` 工具或 `nadc.china-vo.org/.../cutout` URL。仓内**不存在**这类端点（§1 路由全表逐条实测）与工具（§7 恰好 7 个）。这违反 `agents/openai.yaml` 的 `honesty_stance`「降级必须显式标注」「不伪造成功」。
2. **拿 `cone_search` 硬凑"看图"**：`cone_search` 只回源行的表格（ra/dec/各波段星等），既不是像素也不是可打开的图像文件；把它当成"影像"答非所问。
3. **把本地 FITS 当"图"**：`serialization.write_fits` 产出的是 **binary table（表）**，不是图像 FITS；且站点侧根本不支持 `output.fmt=fits`（data-formats.md §1）。"能直接打开看的图"（JPEG/PNG 预览、HiPS 瓦片）本 skill 一律没有。
4. **把 CLI 的"预览"当成图**：`src/__main__.py:360` 的"只预览前 5 条"是**文本行**预览，不是图像预览。
5. **忽略"这个天区"未解析**：直接默认一个坐标去查（甚至默认 (0,0)——`crossmatch_batch` 的注释明确警告 (0,0) 是真实天区，脏输入绝不能静默当赤道原点）。本题即便能力存在也应先要坐标。
6. **误把请求转给 astro-catalog**：那是「通用星表检索/交叉匹配」，同样不出图；生态内影像归约（astro-clean）也不是出图预览服务。转过去只是换个人再拒一次。
